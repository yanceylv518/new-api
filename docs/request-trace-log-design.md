## 本分支的整合约定

元数据来源 `937793a7e`，时间线来源 `9054b1d43`；保留两条来源历史。元数据使用 `request_trace_metadata`（6 列，每次上游尝试一行），时间线使用 `request_trace_timeline`（21 列，每个请求一行）。`logs.other` 与原 Token、计费明细沿用折扣基线；不保存请求、响应或工具参数正文。

旧 `request_traces` 在主库与日志库迁移前按完整列集合识别，分别改名到对应表；未知结构或对应目标表已存在时明确停止，保留原数据。两项功能保持各自的采样、压缩、保留期、状态接口与权限，表单字段独立，配置顺序保存，查询刷新保留未保存输入。元数据写入器透传时间线的心跳、刷新和响应控制，收尾恢复各自原写入器。

元数据详情沿用最新来源的精简展示：不显示请求顶层字段、响应体行、输出字符数、流式展示统计和字段名指纹；保留实际工具调用、上游信息、结束原因和标记。时间线沿用来源最新的四个关键时点视图，不重新引入已取消的阶段详情卡。

2026-10-22 审查修复：OpenAI Chat/Completions SSE 已确认的 HTTP 200 业务错误同步记入当前流式尝试的错误状态，正常 EOF / `[DONE]` 不再将其归为成功；后续重试开始时仍重置尝试结果。元数据中间件内层恢复 panic 时同步标记时间线 `panic` 并结束转发计时。末帧隐藏 usage 时使用独立客户端 DTO，格式化/推理转正文不会重新带回原始用量，计费仍读取原始帧。

## 当前实现与存储约定

下面的早期设计保留为字段和界面参考，实际存储与采集以本节为准：

- 原 `logs` 列和 `logs.other` 的计费、缓存、首字耗时、转换诊断、重试链等内容继续按原逻辑保存。追踪详情写入日志库的 `request_trace_metadata` 表，列表、筛选和统计不查询该表。
- 模型固定使用 `request_trace_metadata` 表名。主库与独立日志库在建表前检查旧 `request_traces` 表：只有旧表时原地改名，保留记录、压缩数据和既有索引；新旧表同时存在时返回错误，等待人工处理，不覆盖或合并数据。全新数据库直接创建新表。升级前停止仍使用旧表名的节点，回退旧程序前需将表名改回。
- 每次上游尝试保存一行，以 `(request_id, attempt)` 唯一关联；未到达上游的失败使用 `attempt=-1`。同一请求的多次尝试通过 `request_id` 查询。普通用户只返回所属请求的最终结果，管理员可查看所有尝试。
- `GET /api/log/trace?request_id=...` 使用现有用户鉴权，并按服务端角色与 `user_id` 裁剪数据。普通用户只获取 `trace`，管理员及 Root 可以获取 `admin_info`。前端只在打开消费或错误日志详情时调用，关闭详情后取消未完成的读取；无记录时保留原详情。
- 日志详情保留请求转换、错误信息、请求、上游、响应及原有 Token、计费明细，继续复用现有 Dialog、DetailSection、DetailRow。界面只展示最终尝试，移除历史尝试折叠区、重复的尝试次数/渠道、客户端信息、响应头耗时和本次尝试耗时；推理 Token 位于原 Token 明细中。请求顶层字段、响应体大小/类型、输出字符数、流式统计行和字段名指纹也不展示。后台仍按尝试保存与鉴权，旧记录不重写。
- 请求形状以客户端原始请求为准，转换不改变这些计数。支持 Responses 的 `instructions`、Completions 的字符串/批量 `prompt`、OpenAI 旧式 `functions/function_call`，以及 Gemini 的驼峰和下划线配置字段。文本字符使用 Unicode 码点计数，包含系统提示和明确的工具结果文本，不把工具参数、二进制媒体或结构化结果序列化为文本估算；多媒体计数表示输入部分的个数。
- 上游响应 ID、实际模型、对象类型、创建时间、指纹与服务等级从原始上游响应提取；协议转换生成的客户端标识不覆盖这些值。推理 Token 同样采用上游明确报告的非负整数，保留缺失与显式 0 的差别，优先标准 details 字段并兼容平铺的 `usage.reasoning_tokens`；不采用转换器补出的 0，不根据正文或输出总量推算。
- 结束原因与结束标记保留客户端实际输出协议的值；Responses 的 `response.done` 兼容结束事件也会记录。Gemini 无独立结束标记，合法的 usage-only 分片不会误报未知格式。SSE 类型判断忽略媒体类型大小写与参数，不根据参数内容误判 JSON。
- 工具统计仅来自实际调用。OpenAI 的空名称增量不会清空先前名称；Responses 的 added/done/最终快照按输出位置去重，内置调用使用明确的调用类型标识。请求中声明但未调用的工具、工具参数和工具结果正文不落入名称统计。拒绝标记会保留上游明确给出的值，内容过滤、输出上限和其他未完成状态分别展示。
- 2026-10-21 字段验证覆盖 OpenAI Chat、Responses、Claude、Gemini 四种主要协议，JSON/SSE、原生与 12 个转换方向、工具调用与拒绝响应合计 64 条实际处理器路径；请求转换、追踪中间件、异步 MySQL 写入和详情权限均参与验证。MySQL 8.4.11 上 255 个相关后端叶用例通过且无竞态、无跳过，前端相关 34 项及类型、lint、格式检查通过。验证使用标准协议夹具与项目真实转换处理器，不代表所有厂商私有字段都可推断；摘要模式有意不采集详细统计，上游没有报告的值保持缺失。本轮未部署或调用真实付费上游。
- 表中保存 request_id、attempt、user_id、created_at 与结构化摘要 data。摘要保留耗时、请求大小、状态、结束原因、请求形状、上游标识、实际工具调用与上报的推理 Token；不再写入 trace.resp_bytes、shape.keys，以及 resp.content_type/content_chars/reasoning_chars/chunks/last_chunk_ms/usage_chunk/keys。历史数据不批量改写，读取时忽略已移除字段；原 logs.other 保持原有格式。
- 追踪表不保存消息、回复、推理文本、工具定义、工具调用参数或上游错误原文，错误只提取类型、错误码和状态；拒答只记录是否发生。请求和响应均不再遍历、缓存或保存字段名集合。
- HTTP 200 内已确认的业务失败另外复用 `logs.content` 保存结构化诊断：`http_status` 保留实际上游状态 200，`event` 标识 error/response.failed/response.error，`error` 只保留 type、code、message、param、status 等核心字段；`reported_status_code` 仅来自错误体明确提供的 status_code/http_status 数字字段，不从错误文字或错误码映射推断。原有说明保存在 note，正常日志与历史日志格式保持兼容；这项错误诊断允许保存脱敏、限长的错误 message，仍不保存整帧、请求、回复或未知 metadata。追踪表继续只保存错误类型/码，不重复保存 message。
- 业务错误采集复用协议处理器已有解码，OpenAI 流式工具统计的同一次解码顺带读取根级 error；Gemini 仅在字节探测命中 error 后提取根级错误，空值和嵌套工具内容不当作失败。状态与追踪开关、采样无关，新一次上游尝试开始前清理上一尝试的诊断。凭据和媒体编码在写入消费/错误日志及其服务端日志前逐字段清理，字段按 UTF-8 边界限长；受限字符串取得独立拷贝，不持有完整响应。列表优先显示“上游失败 · HTTP 200 · 错误码”，详情展示可复制的格式化 JSON 与截断标记，原日志类型、费用统计、用量、退款与重试行为不变。
- 请求工具只保留定义数量与选择策略，不采集或保存可用工具名称列表；旧记录中的 `shape.tool_names` 在读取时忽略，不批量改写历史数据。响应通过 `resp.tool_calls_by_name` 保存实际返回的工具名称及各名称调用次数，继续排除描述、参数 schema、调用参数和结果。OpenAI 流式函数名按调用位置合并分片，Claude/Gemini/Responses 提取对应名称，Responses 完整结束事件可补全名称。名称最多 128 字节，响应最多累计 256 次调用；缺失名称的调用单独显示为“未记录”，不会伪造名称，也不回填旧记录。详情按工具横向排列，空间不足时自动换行，次数使用紧贴工具名的数字徽章，较多条目在限高区域滚动。Gemini 的函数声明按声明项计数。
- 仅请求文本字符数继续按 Unicode 码点统计。响应正文与推理字符数已停止提取；原 Token 明细保留原有组件、条件和 logs/logs.other 字段。上游上报的推理 Token 及同一 usage 对应的输出总量仍按实际返回值保存，不依据字符数推算或改写计费结果。
- 工具定义和调用计数先检查 JSON 数组、对象类型。`tools: null`、`tool_calls: null`、数组中的 null 项以及 `function_call: null` / `functionCall: null` 不计为工具或调用；旧式 `function_call` 的名称和参数均为空时同样忽略，避免兼容网关的占位对象造成误计。真实调用缺失名称时仍保留次数。历史误计记录不依据结束原因或缺失名称自动改写。
- 请求形状仅在需要详细信息时提取，上限为 1 MiB。Chat/Claude 的常规内存 JSON 请求在业务解码后直接提取形状并复制可变标量，协议转换不改变原始统计；摘要档不提前遍历内容。RawMessage、兼容字段、异常下标、磁盘缓存及后续失败升级仍在收尾通过独立 reader 采集，已提取形状不再重读。非流式响应的摘要档采集上限为 64 KiB，完整档及单个 SSE 事件上限为 1 MiB。接入解码复用的处理器在读取前接管采集，上游观察器不再额外缓冲正文；客户端已有完整响应字节时直接提取元数据。未接入路径继续使用有界字节观察器，首次需要缓冲时才按 Content-Length 预留容量，扩容不超过上限；超限或无法解析时标记不完整，不将未采集的统计显示成 0。
- SSE 继续识别协议原始结束原因、HTTP 200 内的业务错误、终止标记及实际工具调用；不累计响应大小、事件数量或末片时间。覆盖 OpenAI Chat/Completions、Claude、Gemini 和 Responses 的常见格式，上游状态、协议、响应头耗时与请求标识仍在公共 HTTP 入口采集。
- `resp.end_marker` 按实际收到的终止标记保存最后一个标记原值，包括 `[DONE]`、`message_stop`、`response.completed`、`response.incomplete` 和 `response.failed`；不依据模型名称或结束原因推断。详情在流式输出下显示具体标记，未收到时明确提示；只有旧 `done` 布尔值的历史记录显示“已收到（未记录具体标记）”，不伪造或回填。该字段位于原摘要 JSON 内，不新增表列，也不保存响应正文。工具名称和数字徽章保持横排换行、限高滚动，首行与标签使用相同行高，列表不保留额外缩进和上下内边距。
- 默认使用摘要档，SSE 对 data 事件做字节级探测，只在非 null 的结束原因、错误或终止标记出现时解析。普通文本、工具和纯 usage 增量不再为统计触发摘要解析；不记录事件数量、末次到达时间或 usage 分片标记。metadata_level 保留 summary/full，用于区别实际工具调用等剩余详细元数据的采集范围。
- 摘要写库保留独立精简投影，读取仍使用 RequestTraceData；已移除字段不再出现在摘要或完整档的新记录中。响应 Content-Type 仅作为处理期间的协议识别状态，不序列化。请求是否已经写出数据用内部布尔值表示，结束与错误识别不依赖被移除的统计字段。
- level=all 且成功采样命中、临时诊断渠道或上游状态码不低于 400 时采集剩余详细元数据；轻量探测发现错误后升级。晚升级保留 capture_upgraded，明确此前工具调用无法补齐，详情隐藏不完整工具计数。
- 客户端仅在实际原样转发路径复用上游观察结果，写出时只更新内部已写出标记；格式转换、强制格式化、推理转正文及 Chat 流调整 usage/DONE 的路径仍独立提取剩余元数据。转发失败与网关错误仍保留错误和不完整标记，不按协议名称推断原样转发。
- SSE 完整行按档位探测或解析，跨块、多行事件使用有界缓冲，不保留正文。保留响应标识、结束与错误、工具及上报 Token 的必要提取；请求消息数量通过遍历统计，清理在 Finish 后直接读取错误标志。
- OpenAI Chat 的工具计费、Token 估算、延迟一帧转发及格式转换共享一次业务解码结果，倒数第二帧 usage 回退、最后帧 usage 删除与原始计费后处理保持原有规则。Chat→Responses 同样合并错误检查和转换前的重复解码。OpenAI Chat、Responses、Claude、Gemini 的已接入原生和转换处理器直接从 DTO 提取常规工具调用、结束原因及终止状态，支持 Responses added/done/最终快照去重、Gemini 每帧独立调用和 OpenAI 工具名称增量。字节扫描只补充字段存在性；推理 Token 从小型 usage 子对象提取，区分 null、缺失与显式 0，不将 DTO 默认值当成上游报告。拒绝扩展、错误、空工具占位、异常下标及未接入格式保留原始解析兜底，不为追踪新增严格 DTO 字段或改变业务解码错误。
- 客户端 SSE 仅在完整档且需要独立采集时构造 DecodedEvent，在整个事件实际写出后采集同一份解码结果；关闭、摘要及原样复用路径继续使用原 CustomEvent，避免额外复制响应结构。写入失败或短写只标记交付不完整，不提前记录尚未交付的完整事件。未识别的类型保留原始解析兜底；不通过重新序列化 DTO 提取追踪。扫描器截获的 `[DONE]` 在所有已解码事件后合入，EOF/Close 先结束传输计时，不提前关闭采集器。
- 非流式 Responses 的原生与转换处理器明确指定上游及客户端为 JSON 采集模式；即使上游误将完整 JSON 标为 `text/event-stream`，仍采集最终工具快照并记录完成。保留原始响应头，客户端成功完整写出后直接提取，不新增正文缓冲；摘要档继续省略工具明细，真实 SSE 使用原来的事件采集路径。
- 删除 SHA-256 事件哈希、事件元数据缓存及其淘汰队列，只保留有界短标识清洗工作区，不缓存正文或 DTO。Gemini 的独立完整工具调用使用工具调用序号区分，不再依赖事件计数。上述调整不恢复已移除的最终用量上报诊断，也不改变消费归类、结算、退款或重试规则。
- OpenAI Chat 最后事件同时包含有效 usage 与 choices 时，保留结束原因、工具、角色、拒绝等事件内容；客户端未要求 usage 时只删除客户端末帧的 usage 字段。归一化与计费后处理仍使用未改写的原始帧，纯 usage 末帧继续按配置省略。
- 请求追踪中间件在保存收尾完成或提前返回后恢复原响应写入器，并清除当前 Gin 上下文对采集器的引用；panic 展开也执行此清理。消费者仍可在处理和收尾过程中读取采集器，最终外部 JSON 格式不变；不通过生产请求主动触发 GC，也不依赖上下文池被下一轮请求复用后才解除引用。
- 响应写入包装器通过 Unwrap 透传底层 HTTP 能力，保留流式读写超时、Flush、Hijack 和全双工支持。
- 启用追踪的请求在采集器存活期间调用现有恢复处理，恢复响应完成后再整理并异步提交追踪；请求体清理遇到 panic 时先标记失败、采集请求形状并释放缓存，再将 panic 交给恢复处理，不提前结束客户端观察器。已发出响应头时保留实际 HTTP 状态，outcome 仍标记失败；成功采样不丢弃这类失败，关闭追踪和未鉴权开关继续生效。
- `RequestTraceConfig` 是一个整体保存的运行时 JSON 设置，字段包括 `level`、`pre_channel_errors_enabled`、`anonymous_errors_enabled`、可选的 `upstream_request_id_headers` 与 `compression_level`。前三项默认值分别为 `errors`、`true`、`false`，自定义响应头默认留空，压缩档位默认 `fast`；旧配置缺少新增字段时沿用默认值。`off` 不采集；`errors` 对成功请求只保存基础摘要、对失败保存详细元数据；`all` 保存所有详细元数据。已关闭消费日志时不为成功请求单独写追踪记录。
- 上游请求 ID 可在“系统设置 → 运维 → 日志维护 → 上游请求 ID 响应头”配置，沿用系统设置的 Root 权限。每行一个名称，最多 16 项、每项最多 128 个 ASCII 字符；服务端校验 HTTP 响应头名、规范化大小写并按首次出现顺序去重。按自定义顺序优先匹配，未命中则依次回退 `X-Oneapi-Request-Id`、`X-Request-Id`、`Request-Id`、`X-Amzn-RequestId`、`X-Goog-Request-Id`。`Nvcf-Reqid` 不再内置，需要时手动添加。此项在关闭追踪时仍用于原日志的上游请求 ID，不因此新增追踪记录。
- 每次上游尝试开始时清空此前的 ID；公共发送入口选定的值同时用于原日志和追踪，响应头复制不会再次用默认头覆盖它。仅选择上游实际返回的响应头值，配置不会向上游发送这些名称或伪造 ID。
- 未到达上游的已鉴权失败和未鉴权失败分别受开关控制；未鉴权记录的 `user_id=0`，只允许管理员读取。预扣费阶段的 403 沿用不主动记录的约定。
- SQLite、MySQL、PostgreSQL 通过现有 GORM 迁移创建新表及索引；ClickHouse 使用按请求与尝试排序的 ReplacingMergeTree，读取使用 FINAL，并沿用日志保留天数配置。日志清理任务同时清理追踪表，关系库按批删除。旧日志不回填，新旧节点部署时应先完成日志库迁移。
- 请求结束时只构建已脱敏的元数据行并交给有界异步队列；队列不持有 Gin 上下文、采集器或正文。每个实例有 2 个写入 worker，总预算为 8192 行及 16 MiB 摘要字符串，包含待写和正在处理的元数据；切片、索引及编码器还有额外内存，不能将该预算解释为整个功能的内存上限。批次最多 128 行或 1 MiB 摘要，每 100 ms 刷新；单个请求的尝试行作为整体入队和写入。
- 队列总预算中预留 1/8 给失败或诊断请求，普通请求最多使用 7168 行/14 MiB，优先请求可使用全部 8192 行/16 MiB；同一请求含失败尝试时整条重试链优先准入。队列达到相应限额、未启动/已停止或单个请求超过批次预算时，整组直接丢弃，累计 dropped_rows，并按请求类别累计 dropped_priority_rows/dropped_regular_rows；返回可识别的 ErrRequestTraceDropped。中间件不逐条打印这些预期丢弃，不执行同步数据库回退。后台每次数据库操作限时 3 秒，暂态错误最多重试一次、等待 100 ms，永久错误不重试。关系库沿用唯一键幂等写入，ClickHouse 继续使用 ReplacingMergeTree；单行 INSERT 跳过 GORM 默认事务，多行使用事务。编码与最终写入失败单独计数并记录服务端错误。预留容量不承诺故障期间不丢记录。
- HTTP 服务停止接收并等待请求结束后，在数据库关闭前给予异步队列 10 秒排空时间；超时会取消剩余写入并报告错误。内存队列不提供崩溃持久性，进程被强制结束、主机断电或排空失败时可能丢失尚未写入的追踪。原消费日志、计费和追踪的持久化时点不同，详情需容许短暂的可见性延迟。
- 日志库默认沿用关系数据库部署，MySQL 和 PostgreSQL 均支持；SQLite 兼容保留。`LOG_SQL_DSN` 为空时沿用主库，也可显式指定独立 MySQL DSN 或 `postgres://` / `postgresql://` 连接。ClickHouse 继续作为可选后端，通过 `clickhouse://` DSN 启用，不因追踪功能自动切换。
- 关系库继续使用无前缀 JSON 或 `zstd-base64-v1:` 加标准 Base64 的存储格式。后台只提供 fast（默认）和 standard，对应 zstd SpeedFastest、SpeedDefault；旧 high/best 配置在读入时映射为 standard，未知值仍拒绝。每个写入 worker 独占一个延迟初始化、并发数为 1 的压缩器，切换档位和退出时释放旧编码器及缓冲，不再永久保留四档全局编码器。直接调用 RecordRequestTraces 的同步调用方为该批次创建并关闭独立压缩器；请求投递不会使用该同步路径。保留 1 MiB 输入与解压上限，历史四档压缩及无前缀 JSON 均可读取，不引入字典或新前缀。ClickHouse 继续写 JSON 并使用数据库原生压缩；logs.other 保持原格式。
- 关系库采用自适应压缩：小于 256 bytes 的摘要直接保存无前缀 JSON；其他记录按所选档位压缩，只有“前缀＋Base64”总字节数小于原 JSON 时才使用压缩格式。两种格式可以在同表共存，读取协议不变。256 bytes 是初始策略值，尚未通过本轮压测确认最优阈值；不以这次代码修改推断 CPU、内存或吞吐改善比例。

### 采样、诊断与运维设置

- `success_sample_rate` 为 0–100 的整数，默认 100，在请求开始时按请求 ID 稳定选择；失败、失败重试链和临时诊断仍绕过成功采样。未命中时只进行摘要档错误探测，最终成功则不构建追踪行；确认失败后按升级规则记录，无法补齐之前略过的详细统计。不以代码检查代替实测推断 CPU、内存或吞吐提升比例。
- `diagnostic_channel_ids` 最多 16 个正整数，`diagnostic_expires_at` 为 Unix 秒，到期自动失效，设置时最多延长至未来 24 小时。命中渠道的尝试保存详细元数据；`level=off` 仍关闭采集，消费日志关闭时不单独保存成功追踪。采集与采样使用请求开始时的配置快照；异步摘要按执行写入时的压缩档位编码。
- `retention_days` 默认 0，不开启独立自动清理；可配置 1–3650 天。开启后复用系统任务的 master 调度、数据库租约、执行记录和失败状态，每小时分批删除超期追踪。保留期改长或关闭时，正在执行的任务停止后续批次；已删除记录不恢复。原有手动日志清理继续同时清理追踪，并显示追踪阶段、已处理条数及后续原日志进度。
- ClickHouse 已有的原生 TTL 仍生效，与定时清理中更早触发的策略决定实际过期时间。延长 `retention_days` 不会恢复已过期数据，也不会延长部署环境配置的 `LOG_SQL_CLICKHOUSE_TTL_DAYS`。
- `GET /api/log/trace/status` 仅 Root 可读取，展示队列、写入中、成功、写入失败、dropped_rows 丢弃、重试、采样跳过、不完整采集及批次耗时，并带最近一次自动清理任务。计数属于当前实例，重启后重置；旧 fallback_rows 字段为兼容保留且恒为 0。丢弃与数据库写入失败分开计数，幂等成功不等于新增行数。
- 详情 API 保持原 `data` 数组并增加 `pending` 布尔值。待写索引按用户归属裁剪；前端打开详情时等待落库，关闭时取消读取。近期请求在空结果时短暂重查，兼容详情被负载均衡到另一实例的情况；仍为空时提供手动刷新，不猜测历史缺失原因。

### 结束状态与耗时口径

- 新摘要包含 `version=1`、可选 `trace.outcome` 和 `admin_info.upstream.ms`。`trace.ms` 仍是请求累计耗时，各次尝试在响应读取结束或转发处理结束时定格单次耗时；旧记录缺少单次耗时时明确显示请求累计口径。
- 结束原因按实际值显示，详情分别标注正常、工具调用、截断、拒答、失败、客户端断开和未知，不将未知值归为正常。`resp.end_marker_policy` 区分需要独立终止标记和协议不适用；Gemini 的 `finishReason` 作为完成信号，不伪造 `[DONE]` 等标记，实际收到的独立标记仍按原值保存。
- `resp.incomplete_reasons` 和 `admin_info.shape_incomplete_reason` 仅记录固定原因码。除大小超限、缓存不可用、JSON 无效、未知格式、工具数量或标识限制外，新增 capture_upgraded（晚升级无法补齐统计）、client_delivery_incomplete（客户端未完整接收）、upstream_read_error（上游读取失败）。读取失败同时保留错误状态，使未命中采样的失败请求仍可被保留。不保存错误正文，旧不完整布尔字段继续兼容。

### 日志库选择

推荐使用 MySQL 或 PostgreSQL 作为默认日志库。日志库类型由启动环境的 `LOG_SQL_DSN` 决定，密码和其他连接选项由部署环境提供：

| 后端 | `LOG_SQL_DSN` 格式 | 请求追踪摘要存储 |
| --- | --- | --- |
| MySQL | `USER:PASSWORD@tcp(HOST:3306)/DATABASE?charset=utf8mb4&parseTime=true` | 自适应 zstd＋Base64，小记录或压缩无收益时保存 JSON |
| PostgreSQL | `postgres://USER:PASSWORD@HOST:5432/DATABASE` | 自适应 zstd＋Base64，小记录或压缩无收益时保存 JSON |
| ClickHouse | `clickhouse://USER:PASSWORD@HOST:9000/DATABASE` | JSON，使用数据库原生压缩 |

未设置 `LOG_SQL_DSN` 时沿用主数据库；SQLite 兼容行为保留。切换后端需要复制历史日志、追踪和审计数据，修改连接配置不会自动搬迁历史数据。应在停止原应用写入后完成复制和完整性核对，再用新配置启动应用；保留原数据库与切换前配置用于恢复。

SQLite 单连接容量限制仍在：64 并发 JSON 持续 45 秒（4542 请求）及内容变化 SSE 8 秒（896 请求）各缺失 1 条追踪，均记录了带请求 ID 的 3 秒写入超时；转发和旧日志写入成功。失败记录保留，没有将独立超时改长或通过重跑替换结果。SQLite 16 并发持续场景无缺失，但吞吐没有改善。

压测使用本地 HTTP 客户端、正式公共上游发送入口及模拟上游；资源计量包含客户端和模拟上游，未测完整鉴权/计费链路的性能。SSE 是固定报文一次返回，未测真实逐事件延迟及逐块 flush；ClickHouse 仅完成功能与迁移验证。结果不能直接用作 VPS 容量。首轮工具连接池缺失造成的临时端口不足等异常，也保留在报告中。

## 2026-10-21：四个转发边界

新记录使用 `measurement_version=3`，只采集四类时间边界，继续以入口单调时钟计算整数微秒偏移：

1. 请求进入 New API。
2. 即将调用上游 HTTP 客户端；包含获取连接、发送请求等工作，不代表请求正文已发送完毕。
3. `GotFirstResponseByte` 收到上游响应首字节，不代表首个 token 或完整响应体；自动重定向保留最终响应的首字节。
4. 响应处理器完成读取、转换和向下游写出之后，结算和消费日志之前。只说明服务端转发结束，不证明客户端已接收完毕。无正文响应在交还响应控制权时结束。

普通 HTTP 请求只在上述四处取时。重试保留每次实际调用的开始与首次响应；失败的调用另记录终止边界。调用准备失败时不伪造上游开始或响应时间。错误响应通过实际写出记录终点；最后一次转发之后发生的上下文取消不再改变已完成转发的结果。时间线入队仍在请求处理结束后进行，但总耗时和墙钟结束时间固定在转发边界，不包含其后的结算、消费日志和异步入库。

不再采集鉴权、读取请求体、限流、定价、预扣费、结算和日志等内部阶段，也不再采集 DNS、连接、TLS、逐块读写时间、分块数量和最大间隔。流式失败、超时、客户端断开以及 HTTP 写出失败仍参与结果判定；`response.failed` 等业务失败继续保留，不能被成功采样丢弃。SSE 正常分块路径不为时间线读取时钟或获取采集锁。响应体不再包装读取计数器；未采集的上游字节数为 null，而非 0。

WebSocket 记录连接调用开始和会话转发结束；握手响应不冒充模型响应首字节。没有可用首字节钩子的通道标记缺失，前端不补零或用响应头就绪时间替代。保留 Writer 的 Unwrap、Flush、Hijack 和写超时能力。

本次沿用 `request_trace_timeline` 的现有 21 列，保留首次输出时间列用于读取历史记录；四点版不再写入该时间，新行保持 NULL。列集合不再要求永久固定，后续字段调整须通过保留历史数据的兼容迁移完成。摘要权限、有限异步队列、采样和 Zstd/Base64 设置保持不变。`trace_data` 的紧凑存储版本仍为 `v:1`，新载荷允许未采集的上游字节数缺省；需要本次新版读取端，先升级读取端再启用新版写入端。既有原文、压缩及紧凑记录继续按原口径展示，不重新计算或回写历史耗时。前端直接显示当前横向时间线，新记录根据四个边界展示准备、等待响应、接收转发三段；移除视图切换页签、阶段／事件表格和独立重试表格，重试仍以调用分段呈现，保留点选分段展开详情。

## 2026-10-18：有限重查与当前节点健康

时间线查询成功返回 found=false 时，前端在弹窗保持打开且响应节点启用采集的条件下，最多再查询三次，间隔依次为 500、1000、2000ms；HTTP/解析失败不自动重试。未找到结果的 staleTime 为 0，已找到的终态记录仍缓存 30 秒。手动刷新重新开始有限重查；关闭弹窗卸载查询观察者，并通过现有 AbortSignal 取消无其他观察者的在途请求及定时器。查询使用 React Query 按请求 ID、权限及查看者身份去重，关闭底层仅按 URL 复用 GET Promise 的机制，避免不同取消信号共用旧请求。未找到仍只说明数据库没有匹配记录，不将它判定为正在写入、已丢弃或已过期。

系统设置的日志维护新增折叠的“时间线采集与落库状态”。展开时才挂载查询，每五秒刷新，页面隐藏或折叠后停止周期请求，错误后暂停并提供手动重试。接口仍由 AdminAuth 保护，显示当前响应节点及本次启动时间，计数不代表全局集群状态；负载均衡可能使两次刷新访问不同节点。

状态包含队列、正在处理/入批、批次等待和写入/重试中的条数，以及总待完成条数。队列容量维持 512，批次上限维持 64；新增的固定大小时间环记录已接受但未完成记录的入队时刻，最老等待使用单调时钟计算，包含后续处理、等待和重试。快照在同一状态锁下形成，满足 outstanding = pending + processing + buffered + writing，以及 accepted = written + failed + dropped_shutdown + outstanding。编码失败、队列满、写入器已停止属于入队前丢弃，单独累计；全部丢弃原因之和对应 dropped。

最近批次耗时从进入 flush 到最终成功/失败，包含数据库调用和重试退避，不包含此前压缩或等待凑批。写入、最终失败和丢弃累计记录条数；重试累计重复的批次写库调用次数，最近失败时间只在批次最终失败时更新。最近成功和失败时间为墙钟 Unix 微秒；没有发生过的时间或耗时返回 null，明确零耗时保留 0。状态只保存在本节点内存，不写入 request_trace_timeline，也不返回原始 SQL 错误、DSN 或凭证。新增状态锁不包围压缩、数据库调用或诊断日志 I/O；不在流式分片路径增加状态打点。

## 2026-10-16：时间线表命名

时间线表统一使用 `request_trace_timeline`，通过显式 GORM `TableName` 固定名称，建表、写入、查询、清理及 ClickHouse 的 TTL/列压缩路径均使用该名称。固定 21 列、既有索引名称、载荷版本及压缩格式保持不变，表改名复用原索引，不额外创建等价索引。

master 启动迁移会检查旧 `request_traces`：只有列集合完整匹配现有 21 列合同且新表不存在时，才将旧时间线表原地改名，历史数据无需复制或重新编码。另一套请求形状追踪的六列表不改名，直接独立创建新时间线表。旧时间线表和新表同时存在时停止迁移并报告冲突，不自动合并或覆盖任何表。迁移中途失败后，重启会根据实际表名继续执行列及索引检查。

旧版节点仍访问旧表名，升级时先停止旧版节点，再由新版 master 完成改名后启动其他新版节点；回滚需要恢复对应表名，不支持两种表名的节点混跑。本次仅修改实现和说明，未在现有数据库执行改名，也未运行新的数据库或行为测试。

代价也需保留：原始 JSON 在未开启传输压缩时发送字节更多，详情查询的服务端 CPU 和单查询峰值内存高于二进制；点查 P95 范围重叠，不能声称原文查询普遍更快。编码墙钟含拷贝，容器 CPU 含后台合并和采集；Windows 进程 CPU 的 0 可能来自计时量化。小批次强制 Wide part 的 INSERT 开销显著，不将其倍率直接套用到生产默认 Compact part。未测原生协议传输压缩、冷缓存或并发详情查询；98.043242% 的 mock trace_data 压缩率也不能直接作为所有生产数据的存储估算。

## 2026-10-15：独立请求时间线第一版

当前实现位于 `custom/rc35-request-timeline`，基于 `704e5970d5f4eaebf0a58458ba436ee800bf6854`。本节定义已接入代码的请求时间线；其后的旧章节保留为请求形状日志的历史方案，其中“不新增表”“写入 logs.other”不适用于当前时间线实现。

### 固定字段合同

`request_trace_timeline` 使用独立日志库 `LOG_DB`；未单独配置日志库时与主库共用数据库。每个入站中转请求形成一条逻辑终态记录，通过 `request_id` 关联零到多条现有日志，不设置跨表外键，不向 `logs.other` 写入追踪数据。

### 采集和终点

- HTTP Handler 外层创建起点与请求 ID，Gin 桥接中间件位于 Recovery 外侧，终态在整个 Gin 调用返回后冻结。沿用同一个响应头和日志请求 ID。
- 仅中转路由落库，包括鉴权失败、限流等未到达消费日志的请求；管理 API、静态资源和追踪查询自身不落库。
- 鉴权、首次正文缓冲读取、限流、分发、校验、计价准备、预扣费、渠道选择、渠道处理、请求准备、响应处理、结算、日志记录及 SQL INSERT 分别记录区间；区间允许重叠，禁止直接求和。
- 通用 HTTP 和 AWS SDK 实际 HTTPClient 使用 httptrace。每次 HTTP 调用独立记录交换，保留重复的网络事件，不把 GetConn 到 GotConn 宣称为纯连接池等待。proxy 只表示渠道是否显式配置代理；环境代理仍可能生效。
- 响应体记录从返回响应头到读完或关闭的观测区间，不把这一范围称为纯生成时间。共享 SSE 扫描器在读取协程本地累计首末事件、数量和最大间隔，退出并等待协程完成后写回；该间隔包含背压影响。
- 下游 Write/WriteString 观察实际返回字节及错误。完成表示服务端应用同步处理结束，不证明客户端完整接收；不包括追踪自身序列化/落库或异步退款等后台工作。
- WebSocket 记录握手及通道会话处理区间；升级后的数据帧写入和未接入的传输/流事件明确标记 partial，不能把缺失当 0。任务提交记录本次 HTTP 和逻辑重试，不把后台任务完成并入 HTTP 时间线。
- 每请求最多 96 个阶段、64 次详细尝试、每次 16 个 HTTP 交换、每交换 64 个网络事件且全请求最多 512 个网络事件；真实尝试计数仍保留。正文外元数据有长度限制，超限或裁剪均标记 partial/truncated。JSON 超过 64 KiB 时先裁剪网络事件，再裁剪交换详情，摘要保留。

请求最终结果以最后一次逻辑尝试为依据；已恢复的重试失败不把最终成功改成失败，panic 和入站上下文的取消/超时优先。原始网络错误在脱敏前分类：响应头前使用 request_timeout/request_canceled，响应体读取阶段使用 read_timeout/read_canceled；这些是 trace_data 中开放字符串的新增值，不改变数据库列或载荷版本。

前端只根据实际观测画区间。重复网络回调无法唯一配对时保留原始事件；提前响应产生的反向区间不绘制；未观测到的连接复用状态及阶段结束保持未知。阶段可能重叠或存在间隙，不能把所有阶段相加解释为总耗时。

### 写入、保留及配置

入口使用共享中转路径分类，静态中转及单段 mode/MJ 路由优先保留；插件禁止注册的管理/前端命名空间直接旁路，不创建 collector、Context 取消回调或 Writer 包装。未知路径继续采集并由 Gin 的 relay 标记或 FullPath 二次确认，避免插件热更新与入口判断之间的竞态造成漏采。

`request_trace.success_sample_rate` 默认为 100，范围 0–100；使用 FNV-1a 64 位 request_id 哈希模 100，与 metadata 的普通成功采样算法一致。入口快照配置，Freeze 后、编码前决定是否保留。非 success、partial 或真实尝试数大于 1 的记录不参与概率采样。`request_trace.slow_request_ms` 只保留达到阈值的非流式请求，`request_trace.slow_first_byte_ms` 使用最终尝试首字节相对网关入口的偏移，包含前期准备及此前重试；两者默认 0（关闭），范围 0–86400000 毫秒。长流正常生成时间不触发总耗时规则。主动排除计入 sampled_out，不计 dropped；绕过采样仍可能因背压或数据库失败未持久化。

512 条队列之外增加 16 MiB 原始载荷预留预算，覆盖全部已接收且尚未最终完成的记录，包括压缩、批次及 SQL 重试。压缩结果仅在比原文小的时候使用，因此始终按原始载荷大小预留，成功或最终失败时释放；强制关停清空预算。预算不包含采集器、请求协程编码临时对象、字符串元数据、单 worker 编码器及数据库驱动内存，不等同于整个进程内存上限。仍使用一个异步写入 worker，保持 FIFO 健康统计和批次收尾语义。

新记录使用独立的紧凑存储版本 `v:1`：短键、可空字段省略缺失值，微秒整数及全局事件序号完整保留；明确的 0、false 和数组顺序不丢失。解码后恢复原有公开 Data，前端仍接收显式 null 与原字段名，schema_version 和 measurement_version 不变。历史原文 JSON 与 Zstd/Base64 保持可读。新格式需要新版读取端；多节点升级或回滚应先部署支持新格式的读取端，再启用新版写入端，旧版节点仍可读取固定摘要但不能解码新详情。原文缩小不代表最终 Zstd 体积或 CPU 按同一比例下降，收益须另行测量。

详情查询直接将存储载荷解码为公开 Data，不再经过“恢复标准 JSON → 控制器再次解码”的中间转换。紧凑格式必需的版本、方法、路由、响应和采集覆盖对象，以及嵌套的必填标量必须存在且类型正确；缺失或 null 不得伪装成真实零值。空路由、明确的 0/false、可空观测时间和无观测的空数组保持原语义；损坏详情返回 invalid_data，摘要仍可读取。字节读取接口保留有效历史 JSON 的原文字节，包括未知字段及空白。

尾部采样后先在短锁内检查已停止、预算已完全耗尽或队列已满，再构造紧凑对象和编码；这些情况下直接分类拒绝。编码后的最终入队仍复核停止状态、实际字节预算及队列容量，不预留估算大小、不在锁内编码。超过 64 KiB 时在同一份紧凑对象上先删除网络事件、必要时再删除交换明细，并按每次编码后的真实大小判断；保留 partial/truncated 标记，公开记录同步更新，避免重复构造各层数组。

| 环境变量 | 默认值 | 行为 |
| --- | --- | --- |
| REQUEST_TRACE_ENABLED | true | 未保存 request_trace.enabled 时的采集默认值；保存后的系统设置优先 |
| REQUEST_TRACE_RETENTION_DAYS | 7 | 1–3650 天；关系库由 master 分批清理，有积压时续跑，ClickHouse 使用 TTL |

系统设置 → 运维设置 → 日志维护提供“请求时间线压缩”选项，适用于关系型日志库，沿用现有系统设置接口及权限，持久化键为 `request_trace.compression_level`。默认 `fastest`，允许 `fastest`、`default`、`better`、`best` 四档，分别对应当前 Go 库的 `SpeedFastest`、`SpeedDefault`、`SpeedBetterCompression`、`SpeedBestCompression`。服务端在写入配置前校验枚举，配置事务提交成功后更新内存；其他节点沿用已有选项同步周期。修改后，使用关系型日志库的节点后续出队记录采用新档位，无需重启，不重写历史记录；ClickHouse 不读取该档位。

关系型日志库每条记录使用独立 Zstd 帧并启用校验和，不使用跨请求字典；写入协程只持有一个单并发编码器及可复用缓冲区，切换档位时释放旧编码器。压缩帧转为标准 Base64 后使用以下 JSON 封装，`raw_bytes` 为解压前原始 JSON 的 UTF-8 字节数：

```json
{"codec":"zstd-base64","raw_bytes":1544,"payload":"..."}
```

只有完整封装文本比原始 JSON 更小时才保存压缩形式；压缩失败记录诊断并保留原始 JSON。压缩不会删除阶段、精度或其他字段，原有采集上限和裁剪规则保持不变。读取时自动识别历史原始 JSON 与压缩封装，严格校验 Base64、Zstd 校验和、解压大小及 `raw_bytes`，解压输出和窗口最多 64 KiB。损坏或不支持的载荷保留摘要，并返回现有 `invalid_data` 详情状态。普通用户只读取摘要，不需要解压。

`schema_version` 仍表示解压后的时间线 JSON 版本，压缩格式由 `codec` 标识，不增加或删除数据库列。所有档位均可互相读取。尚未接入解压的旧版服务只能展示压缩记录的摘要，多节点部署及回滚时需确保处理详情查询的节点具备解码支持。

正常关停先等待 HTTP 请求，再限时排空追踪队列并停止清理协程，最后关闭数据库。队列是进程内数据，节点异常退出存在丢失窗口；完成后异步落库也存在短暂可见性延迟。在主节点完成建表后再启动依赖新表的其他节点。

### 查询及展示

- `GET /api/request-traces/:request_id`：管理员查询完整已允许的阶段和网络元数据。

## 1. 背景与目标

现有用量日志能回答"谁、用哪个模型、走哪个渠道、花了多少、报了什么错"，但几乎不记录请求和响应本身的形状，并且相当一部分失败请求不进 `logs` 表。排查问题时经常只有一句错误消息。

目标：

1. 每条请求日志附带足够定位问题的元数据：大小、状态、毫秒级耗时、结束原因、请求形状统计、上游返回的关键标识。
2. 未到达渠道的失败也能在日志页按请求 ID 查到。
3. 不保存请求体和响应体正文。
4. 不改 `logs` 表结构，不新增表。
5. 对热路径的开销可忽略，存储增量可通过开关控制。

## 2. 非目标

- 不保存请求体、响应体正文或其片段。唯一的原文是失败时上游返回的错误响应体（见 4.4）。
- 不保存上游响应头（限流头、`retry-after`、`cf-ray` 等）。
- 不给用量日志列表加列，不加筛选项，不做基于这些字段的统计报表。
- 不覆盖异步任务（视频生成、Midjourney 等）的提交与轮询日志。这条路径本次未分析。
- 不覆盖 Realtime WebSocket 的响应字节统计。
- 不引入独立追踪表、对象存储或采样系统。

## 4. 数据设计

所有新增字段都写在 `logs.other` 里，分三处：`other.trace`（用户可见）、`other.admin_info.trace`（管理员）、`other.root_info`（Root）。字段名为提案。

通用规则：

- 取不到或为零的可选项不写入，前端也不显示对应的行。例外是消息条数，为 0 时也保存。
- 整个子对象为空时省略该键。
- 旧日志没有这些字段，前端按"有才显示"渲染，不需要回填。

### 4.1 用户可见：`other.trace`

| 字段 | 类型 | 含义 | 何时写入 |
| --- | --- | --- | --- |
| `ms` | int | 从请求开始到本条日志写入的毫秒数 | 始终 |
| `req_bytes` | int | 解压后的请求体字节数 | 已读取请求体时 |
| `resp_bytes` | int | 写回客户端的字节数 | 成功日志 |
| `finish_reason` | string | 上游给出的结束原因原值；流被中断未收到时为空串 | 成功日志 |
| `stage` | string | 失败阶段：`auth`、`rate_limit`、`validate`、`price`、`pre_consume`、`select_channel`、`upstream` | 错误日志 |

`finish_reason` 统一保存各协议的原值：OpenAI 的 `finish_reason`、Claude 的 `stop_reason`、Gemini 的 `finishReason`，不做跨协议归一。

`shape.keys` 用来替代"保存请求体片段"。它不含任何值，能直接看出必填字段拼错、把一种协议的请求体发到另一种协议的接口这两类问题。JSON 本身损坏时解析不出字段名，这种情况只能依靠错误消息。

### 4.3 多媒体计数的来源

请求解析时已经把多媒体输入分成图片、音频、视频、文件四类（`relaykit/types/request_meta.go:6`）。各协议的识别位置：

| 请求格式 | 视频的识别方式 | 位置 |
| --- | --- | --- |
| OpenAI 兼容 | 内容分片类型为 `video_url` | `relaykit/dto/openai_request.go:227` |
| Gemini 原生 | 内联或引用数据的 MIME 类型为视频 | `relaykit/dto/gemini.go:90` |
| Claude 原生 | 协议不支持视频输入 | — |

视频通常以地址传入，请求体很小，日志里只能知道"带了几个视频"，拿不到视频的大小、时长和分辨率。

### 4.4 Root 可见：`other.root_info`

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `upstream_error_body` | string | 上游错误响应体原文，截断到 4096 字节，写入前经 `common.MaskCredentials` 脱敏 |
| `upstream_error_body_truncated` | bool | 是否被截断 |

只在失败记录上保存，受单独的开关控制。它的内容是供应商的报错文本，不含用户的提示词。前端沿用现有的"Root 诊断"分区展示。

### 4.5 明确不保存的内容

- 请求体与响应体正文，包括截断片段。
- 令牌和渠道密钥。
- 终端用户标识（OpenAI 的 `user`、Claude 的 `metadata.user_id`）。
- 工具定义、工具调用参数。
- 多媒体的地址和数据。
- 上游响应头。

### 4.6 修正：识别 Anthropic 的上游请求 ID

`relay/channel/api_request.go:552` 和 `service/http.go:28` 在 `X-Oneapi-Request-Id`、`X-Request-Id` 之外补充识别 `request-id`，写入现有的 `upstream_request_id` 列。这是独立的缺陷修复，不受追踪级别控制。

## 5. 未到达渠道的失败落库

这类失败写成一条普通的错误日志，全部使用 `logs` 表现有的列，不改表结构。

| 现有列 | 填什么 |
| --- | --- |
| `type` | 5，现有的"错误"类型 |
| `user_id`、`username`、`token_id`、`token_name` | 已鉴权的填实际值；未鉴权的填 0 和空串 |
| `model_name` | 能解析出来就填，否则为空 |
| `channel` | 0 |
| `quota`、`prompt_tokens`、`completion_tokens` | 0 |
| `request_id` | 返回给客户端的请求 ID |
| `content` | 错误消息，经 `common.MaskCredentials` 脱敏 |
| `ip` | 已鉴权的沿用"用户是否开启记录 IP"；未鉴权的直接记录来源 IP |
| `other` | `status_code`、`error_code`、`error_type`、`request_path`，以及 4.1、4.2 中能取到的字段 |

按能否归属到用户分两档，各配开关：

| 档位 | 包含 | 默认 | 理由 |
| --- | --- | --- | --- |
| 已鉴权的失败 | 请求校验失败、无可用渠道、用户限流、敏感词、计价错误 | 开 | 能归属到用户和令牌，数量受用户自身请求量约束 |
| 未鉴权的失败 | 令牌无效、IP 限流 | 关 | 不属于任何用户，被扫描时量可能很大 |

额度不足（403）默认仍不记录：余额耗尽的用户持续重试时每次都会写一行。待确认是否需要单独开关放开。

对用户侧的影响：

- 用户会在自己的日志页看到已鉴权的失败记录。
- 未鉴权的记录 `user_id` 为 0，不属于任何用户，只有管理员和 Root 能看到。
- 用量、RPM、TPM 统计只查 `type = 2` 的消费记录（`model/log.go:680`、`model/log.go:722`），不受新增错误行影响。

所有错误日志仍受现有的 `ERROR_LOG_ENABLED` 总开关约束：它关闭时，本节的记录同样不写。

## 7. 后端实现要点

### 7.1 采集点

| 数据 | 采集位置 | 说明 |
| --- | --- | --- |
| `trace.ms` | 上下文里已有的请求开始时间 | `processChannelError` 已在用同一个时间点 |
| `trace.req_bytes` | `common.GetBodyStorage(c).Size()` | 请求体已缓存，取大小是常数时间 |
| `client.*` | 请求进入时的请求头 | 解压中间件会删除 `Content-Encoding` 头（`middleware/gzip.go:91`），必须在它之前或之内记下 |
| `trace.resp_bytes` | gin 的 `c.Writer.Size()` | 流式时包含保活的 ping 帧；未写出任何内容时返回 -1，需按 0 处理 |
| `attempt` | `RelayInfo.RetryIndex` | 已存在 |
| `upstream.status` / `proto` / `header_ms` / `req_bytes` | `relay/channel/api_request.go:532` 的 `doRequest` | 所有走通用请求路径的渠道一处覆盖 |
| `shape.*` | 各请求 DTO | 见 7.2 |
| `shape.keys` | 请求校验失败的返回处 | 见 7.3 |
| `finish_reason`、`resp.*` | 各协议的流式与非流式响应处理 | 见 7.4 |
| `upstream_error_body`、`upstream.error_type` | `service/error.go:87` 的 `RelayErrorHandler` | 见 7.5 |

采集结果挂在 `RelayInfo` 上的一个追踪结构里，在生成日志 `other` 时写入。成功日志的入口是 `service/log_info_generate.go` 的 `GenerateTextOtherInfo`，错误日志的入口是 `controller/relay.go` 的 `processChannelError`，两处共用同一个写入函数，由它按级别决定写哪些层。

### 7.2 请求形状的轻量计数

现有的 `TokenCountMeta` 已包含消息数、工具数和文件列表，但只有在开启 token 统计或敏感词检查时才完整生成；其余情况走只取 `max_tokens` 的快速路径（`controller/relay.go:136`）。完整生成会拼接全部文本，开销不小。

需要为每种请求 DTO 提供一个只计数、不拼接文本的方法：遍历消息累加文本长度并按类型数多媒体个数。它的成本与消息条数成正比，不复制内容。级别为 `off` 时不调用；级别为 `errors` 时只在写错误日志时调用。

### 7.3 顶层字段名

只在请求校验失败时执行：把请求体解析成"字段名到原始值"的映射后只取键。约束：

- 请求体超过 1 MiB 时跳过。
- 最多保存 32 个字段名，每个最长 64 字符。
- 解析失败时不写入该字段。
- JSON 解析必须走 `common/json.go` 的封装。

### 7.4 结束原因与响应统计

这是改动面最大的一项：OpenAI 兼容、Claude、Gemini、Responses 四种协议各有流式和非流式两条处理路径，需要在各自解析响应的位置把结束原因、响应 ID、实际模型、选项数、工具调用数写到追踪结构上。部分位置已经在读取这些值（例如 `relay/channel/claude/relay-claude.go:97`、`relay/channel/gemini/relay-gemini.go:257`），只需顺手记录。

回复字符数优先复用流式处理中已有的累计文本；没有累计的路径按分片累加长度。实现时需逐条路径确认。

未覆盖到的渠道适配器保持字段缺省，前端不显示对应的行，不影响其他功能。

### 7.5 上游错误原文

`RelayErrorHandler` 已经读入完整的错误响应体。在这里截取前 4096 字节，随错误对象带回 `processChannelError`，经 `common.MaskCredentials`（传入当前渠道密钥）脱敏后写入 `root_info`。

`NewAPIError` 定义在 `relaykit/types/error.go:90`。给它加载体属于 `relaykit` 的公开接口变更，必须按项目规则单独验证：

```bash
cd relaykit && GOWORK=off go build ./...
```

### 7.6 未到达渠道的失败

- 中间件的统一拦截点 `abortWithOpenAiMessage`（`middleware/utils.go:14`）里补一次错误日志写入。鉴权、限流、渠道分发三个中间件在入口处各自标记当前阶段，拦截点读取后写入 `trace.stage`。
- 全局与 IP 限流没有走这个拦截点（`middleware/rate-limit.go:143`），需要单独补调用。
- `controller/relay.go` 里进入重试循环之前的几处提前返回（`:115`、`:142`、`:159`）和循环内选不到渠道的分支（`:200`）补调用。
- 是否已鉴权按上下文里是否有用户 ID 判断。
- 每个请求最多写一条这类记录。
- 未鉴权档按来源 IP 做每分钟限量，超出后丢弃并在本地日志计数。限量值待确认，建议每 IP 每分钟 10 条。

记录令牌无效这类事件属于认证审计。按 `AGENTS.md` 的认证安全要求，实现前需阅读 OWASP 的认证与会话管理速查表，并确保记录里不含令牌本身。本设计不保存 `Authorization` 头的任何部分。

## 9. 性能与容量

以下为根据代码和原型示例数据的推算，未做压测。

每条日志 `other` 的 JSON 字节数：

| 记录 | 现在 | 级别 `all` | 加上游错误原文 |
| --- | --- | --- | --- |
| 非流式成功 | 148 | 755 | — |
| 流式成功 | 236 | 764 | — |
| 限流错误 | 156 | 528 | 859 |
| 校验失败 | 117 | 366 | — |

"现在"一列省略了部分计费字段，真实值更大，但增量是准的：级别 `all` 每条约多 400 到 600 字节，级别 `errors` 的成功日志约多 80 字节。上游错误原文最坏 4 KB，只出现在失败记录上。

| 环节 | 影响 |
| --- | --- |
| 写入 | 每个请求仍只写一条日志，写入发生在响应返回之后（`model/log.go:103`），不影响用户感知的延迟 |
| 列表查询 | 筛选和排序都走已有索引列，不读 `other`；每页多返回几十 KB |
| 统计查询 | MySQL 和 PostgreSQL 里行变宽后，按时间范围扫描的统计查询会按行宽增长的比例变慢；ClickHouse 是列存，不受影响 |
| 行数 | 未到达渠道的失败落库会增加行数，对表和每个索引都有成本，影响大于行宽 |

按级别 `all` 估算：每天 10 万条日志约多 50 MB，每天 100 万条约多 500 MB。

## 10. 兼容性与约束

- **数据库**：不改表结构，SQLite、MySQL、PostgreSQL、ClickHouse 都不需要迁移。`other` 是未限长的文本列。按项目规则这类改动不触发三库迁移验证，但仍需在三种关系库上各跑一次写入与读取，确认 JSON 文本往返无损。
- **新旧节点混跑**：旧节点读到新日志时，未知字段随所在层一起被保留或裁剪，行为正确。旧前端忽略未知字段。
- **旧日志**：没有追踪字段，前端各分区不渲染，无需回填。
- **`relaykit` 独立性**：7.5 涉及 `relaykit` 公开类型，需单独构建验证。
- **JSON**：所有序列化与反序列化走 `common/json.go` 的封装。
- **回退**：把级别设为 `off` 即恢复现有行为；已写入的追踪字段留在历史日志里，不影响任何功能。

## 11. 测试计划

后端，优先扩展现有测试文件，新增测试文件不超过一个：

- 追踪结构到 `other` 的写入：三种级别 × 成功与失败，断言各层出现的字段；零值与空对象省略。

- 未到达渠道的失败：两档开关各自生效；`ERROR_LOG_ENABLED` 关闭时不写；每个请求最多一条；未鉴权档的 IP 限量。
- 请求形状计数：四种协议各一个带多媒体与工具的请求，断言各项个数；不含的项不出现。
- 顶层字段名：拼错的必填字段出现在列表里；超过大小上限时跳过；损坏的 JSON 不写入。
- 上游请求 ID：响应头为 `request-id` 时被识别，且优先级低于 `X-Oneapi-Request-Id`。

## 12. 实施拆分

按可独立提交、独立验证的顺序：

1. 设置项与追踪结构；写入无需解析响应即可得到的字段（耗时、请求体大小、响应体大小、客户端信息、尝试序号、上游状态与协议、响应头耗时）；三种级别。
2. 请求形状的轻量计数；校验失败时的顶层字段名。
3. 各协议的结束原因与响应统计。
4. 上游错误原文与上游错误类型；Anthropic 上游请求 ID 的识别。
5. 未到达渠道的失败落库与两档开关。
6. 前端：类型、详情弹窗分区、后台设置、七种语言、测试。

第 3 步改动面最大，可以按协议拆成多次提交。第 4 步里的上游请求 ID 识别是独立修正，可以提前单独合入。

## 13. 讨论中已确定的决定

- 请求体和响应体正文不保存，也不保存截断片段。
- 失败时只保留上游错误原文；请求侧用顶层字段名列表代替请求体片段。
- 上游响应头整组不保存。
- 列表不加列；耗时沿用现有的列，请求与响应大小、结束原因只在详情里显示。
- 详情弹窗沿用现有布局与组件，只增加分区和行。
- 图片、工具、视频等统计项没有时不保存、不显示。
- 全部新增字段放在 `logs.other`，不改表。
- 未到达渠道的失败用现有的列写成错误日志。

## 14. 待确认

1. 请求追踪级别的默认值。取决于日请求量和日志库类型：量小或使用 ClickHouse 可以默认 `all`；每天百万级且使用 MySQL 或 PostgreSQL 建议 `errors`。
2. 额度不足（403）是否需要一个单独的开关放开记录。
3. 未鉴权档的每 IP 每分钟限量值。
4. 详情弹窗里重试的逐次尝试，是按请求 ID 再查一次，还是只显示当前这一条。
5. 请求头白名单是否保留 `anthropic-version` 等三项。
6. 在哪个分支上实现：沿用当前分支，或按既有约定新开 `custom/rc35-request-trace`。

## 15. 风险

- **各渠道适配器覆盖不全**：结束原因和响应统计依赖各协议的处理代码，冷门渠道可能缺字段。缓解：字段缺省时前端不显示，不阻塞其他功能。
- **`resp_bytes` 不等于上游响应大小**：它是写回客户端的字节数，经过格式转换后与上游原始大小不同，流式时还包含保活帧。文案上写"响应体大小"时需在提示里说明口径。
- **未鉴权日志被刷量**：依赖默认关闭和按 IP 限量。开启前应确认日志清理策略。
- **统计查询变慢**：行变宽对 MySQL 和 PostgreSQL 的范围统计有影响，上线后需观察；必要时把级别降到 `errors`。
- **上游错误原文里的敏感信息**：部分上游会在错误体里回显请求片段或账号标识。缓解：仅 Root 可见、凭证脱敏、可整体关闭。脱敏只覆盖凭证，不覆盖回显的用户内容。
