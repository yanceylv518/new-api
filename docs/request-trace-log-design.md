# 请求追踪日志设计

原稿日期：2026-10-09。原稿基线为 `custom/rc35-user-model-discount` 的 `3cf493fbe`。

## 2026-10-18：有限重查与当前节点健康

时间线查询成功返回 found=false 时，前端在弹窗保持打开且响应节点启用采集的条件下，最多再查询三次，间隔依次为 500、1000、2000ms；HTTP/解析失败不自动重试。未找到结果的 staleTime 为 0，已找到的终态记录仍缓存 30 秒。手动刷新重新开始有限重查；关闭弹窗卸载查询观察者，并通过现有 AbortSignal 取消无其他观察者的在途请求及定时器。查询使用 React Query 按请求 ID、权限及查看者身份去重，关闭底层仅按 URL 复用 GET Promise 的机制，避免不同取消信号共用旧请求。未找到仍只说明数据库没有匹配记录，不将它判定为正在写入、已丢弃或已过期。

系统设置的日志维护新增折叠的“时间线采集与落库状态”。展开时才挂载查询，每五秒刷新，页面隐藏或折叠后停止周期请求，错误后暂停并提供手动重试。接口仍由 AdminAuth 保护，显示当前响应节点及本次启动时间，计数不代表全局集群状态；负载均衡可能使两次刷新访问不同节点。

状态包含队列、正在处理/入批、批次等待和写入/重试中的条数，以及总待完成条数。队列容量维持 512，批次上限维持 64；新增的固定大小时间环记录已接受但未完成记录的入队时刻，最老等待使用单调时钟计算，包含后续处理、等待和重试。快照在同一状态锁下形成，满足 outstanding = pending + processing + buffered + writing，以及 accepted = written + failed + dropped_shutdown + outstanding。编码失败、队列满、写入器已停止属于入队前丢弃，单独累计；全部丢弃原因之和对应 dropped。

最近批次耗时从进入 flush 到最终成功/失败，包含数据库调用和重试退避，不包含此前压缩或等待凑批。写入、最终失败和丢弃累计记录条数；重试累计重复的批次写库调用次数，最近失败时间只在批次最终失败时更新。最近成功和失败时间为墙钟 Unix 微秒；没有发生过的时间或耗时返回 null，明确零耗时保留 0。状态只保存在本节点内存，不写入 request_trace_timeline，也不返回原始 SQL 错误、DSN 或凭证。新增状态锁不包围压缩、数据库调用或诊断日志 I/O；不在流式分片路径增加状态打点。

## 2026-10-16：时间线表命名

时间线表统一使用 `request_trace_timeline`，通过显式 GORM `TableName` 固定名称，建表、写入、查询、清理及 ClickHouse 的 TTL/列压缩路径均使用该名称。固定 21 列、既有索引名称、载荷版本及压缩格式保持不变，表改名复用原索引，不额外创建等价索引。

master 启动迁移会检查旧 `request_traces`：只有列集合完整匹配现有 21 列合同且新表不存在时，才将旧时间线表原地改名，历史数据无需复制或重新编码。另一套请求形状追踪的六列表不改名，直接独立创建新时间线表。旧时间线表和新表同时存在时停止迁移并报告冲突，不自动合并或覆盖任何表。迁移中途失败后，重启会根据实际表名继续执行列及索引检查。

旧版节点仍访问旧表名，升级时先停止旧版节点，再由新版 master 完成改名后启动其他新版节点；回滚需要恢复对应表名，不支持两种表名的节点混跑。本次仅修改实现和说明，未在现有数据库执行改名，也未运行新的数据库或行为测试。

## 2026-10-16：精确数值、多视图与采集口径

本次修正沿用固定 21 列和 `schema_version=1`。新载荷增加可选的 `measurement_version=2`，用于说明观测边界；没有该字段的历史记录按旧口径展示并提示，不重写历史记录。此字段属于 `trace_data`，不涉及数据库列迁移。

- 时间始终以整数微秒记录。前端统一显示为毫秒及完整三位小数，例如 `0.736 ms`、`12345.678 ms`，通过整数商和余数拼接，不取整、不显示 `<1 ms`，也不自动切换为舍入后的秒。字节数同样显示原始整数。
- `duration_us` 由单调时钟取得；新版 `finished_at_us = started_at_us + duration_us`，表示入口墙钟时间沿单调耗时推导的结束时间。不能将其理解为另一台机器对客户端收包完成的确认，也不能据此证明硬件计时误差小于 1 微秒。
- 请求起点为最外层 HTTP Handler 开始执行，终点为整个 Gin 调用返回后封口。不包含此前的连接建立和请求头接收，也不包含封口后追踪数据序列化、压缩和异步落库。TCP 最终发送、对端接收及界面显示不在服务器观测范围内。
- 首次渠道选择在分发阶段内、实际处理固定渠道或候选渠道的位置记录；控制器只对确实再次执行选择逻辑的调用记 `channel_select`。首轮选渠归于网关准备，重试前的选渠可纳入对应的派生分组，但不改变原始尝试起点。
- 用量核算函数的包含式区间使用 `usage_finalize`。同步 `SettleBilling` 调用单独使用 `billing_settle`，日志继续使用 `consume_log`、`error_log`、`log_insert`。实际数据库操作和后续后台任务是否同步完成，仍取决于既有计费与批处理路径；这些阶段不声称异步任务已经持久化。历史 `settlement` 明确标为“结算与用量日志（旧口径）”。
- 阶段、响应写出及网络回调尽量在等待采集锁之前取时间；同一次首字节回调的事件时间和摘要值使用同一次采样。取消仍是网关观察到上下文取消的时间，不等于客户端实际断开的物理时刻。
- 未显式观测到尝试结束时保留 `end_us=null` 并标记 `unfinished_attempt`，不以请求结束补齐。上下文已取消而回调尚未观测时保留取消时间为空，并标记 `cancel_time_not_observed`。历史记录可能含旧版补值，界面会提示。
- 流式行时间在 `scanner.Scan()` 返回后立即采样，随后仅统计符合条件且非 `[DONE]` 的数据行。行间隔包含网关读取调度及本地背压，不能全部归因于上游生成；不足两条数据时最大间隔不作为零耗时展示。首个响应头字节、首条数据行、首次内容写出是不同的观测点，均不保证等于首个模型 token。

管理员通过 Tabs 切换“瀑布图、阶段明细、事件列表”。三种视图共用同一查询结果，普通用户仍只获得原有权限范围内的摘要。瀑布图全程使用统一线性刻度，聚焦只改变显示窗口，条形不设虚增的最小宽度；分组区间标为派生值，未观测结束使用虚线，禁止父子区间相加。事件列表按已记录的偏移排序，等时刻不推定并发回调的先后关系，未记录的点不补零。

阶段树、阶段索引和事件投影按数据及语言缓存；各视图按需挂载，表格和瀑布图默认每页 50 行。前端不提供原始 JSON 查看或复制入口，也不为展示原文额外序列化；底层记录继续用于生成三个视图。行组件使用稳定的选择/折叠回调和记忆化，减少选择阶段时的重复渲染；这些是结构性优化，不代表已取得新一轮性能测量结果。

## 2026-10-16：ClickHouse 原文与原生列压缩接入

ClickHouse 日志库的新时间线直接保存原始 JSON；异步写入协程按启动时确定的日志库类型跳过逐条 Zstd、Base64 封装和应用压缩档位读取，不创建应用编码器。请求采集、64 KiB 原文上限、批次字节上限、重试及队列计数沿用现有行为。

新表显式声明 `trace_data String CODEC(ZSTD(1))`。已有表通过固定 21 列检查后，从 system.columns 读取 compression_codec；只有与 CODEC(ZSTD(1)) 不同时执行 `ALTER TABLE request_trace_timeline MODIFY COLUMN trace_data CODEC(ZSTD(1))`。此操作只更新列压缩元数据，不增加或删除字段，不改变 String 类型及载荷版本。启动时不强制 OPTIMIZE、不全量重写历史 JSON；旧数据块保留其原来的物理编码，后续正常合并采用新 codec。

历史 Zstd/Base64 封装继续由既有读取器自动识别，和新原文记录混合查询；原有摘要权限、解压上限及无效数据降级不变。已有记录的应用压缩封装内容不会因列 codec 修改而自动变回原文。

ClickHouse 写入在模型边界使用临时投影，将 `is_stream` 的可空布尔值映射为 `*uint8`，将 `http_status` 映射为 `*int32`，与既有 `Nullable(UInt8)`、`Nullable(Int32)` 列匹配。固定表模型、21 列及对外布尔类型不变；`false` 写作 0，未观测值继续写 NULL。原生驱动不支持把 `*bool` 直接追加到 UInt8，忽略这一差异会使整批时间线写入失败，即使业务请求成功。

关系型日志库继续使用默认快速档和管理员选择的应用压缩档位。设置页用七种语言明确该选项只作用于关系型日志库，ClickHouse 固定使用原文与原生 ZSTD(1)。数据库类型配置需要重启服务，压缩档位仍按原有机制对关系库后续出队记录生效。

## 2026-10-15：独立请求时间线第一版

当前实现位于 `custom/rc35-request-timeline`，基于 `704e5970d5f4eaebf0a58458ba436ee800bf6854`。本节定义已接入代码的请求时间线；其后的旧章节保留为请求形状日志的历史方案，其中“不新增表”“写入 logs.other”不适用于当前时间线实现。

### 固定字段合同

`request_trace_timeline` 使用独立日志库 `LOG_DB`；未单独配置日志库时与主库共用数据库。每个入站中转请求形成一条逻辑终态记录，通过 `request_id` 关联零到多条现有日志，不设置跨表外键，不向 `logs.other` 写入追踪数据。

### 采集和终点

- HTTP Handler 外层创建起点与请求 ID，Gin 桥接中间件位于 Recovery 外侧，终态在整个 Gin 调用返回后冻结。沿用同一个响应头和日志请求 ID。
- 仅中转路由落库，包括鉴权失败、限流等未到达消费日志的请求；管理 API、静态资源和追踪查询自身不落库。
- 鉴权、首次正文缓冲读取、限流、分发、校验、计价准备、预扣费、渠道选择、渠道处理、请求准备、响应处理、结算、日志记录及 SQL INSERT 分别记录区间；区间允许重叠，禁止直接求和。
- 通用 HTTP 和 AWS SDK 实际 HTTPClient 使用 httptrace。每次 HTTP 调用独立记录交换，保留重复的网络事件，不把 GetConn 到 GotConn 宣称为纯连接池等待。proxy 只表示渠道是否显式配置代理；环境代理仍可能生效。
- 响应体记录从返回响应头到读完或关闭的观测区间，不把这一范围称为纯生成时间。共享 SSE 扫描器在读取协程本地累计首末事件、数量和最大间隔，退出并等待协程完成后写回；该间隔包含背压影响。
- 下游 Write/WriteString 观察实际返回字节及错误。完成表示服务端应用同步处理结束，不证明客户端完整接收；不包括追踪自身序列化/落库或异步退款等后台工作。
- WebSocket 记录握手及通道会话处理区间；升级后的数据帧写入和未接入的传输/流事件明确标记 partial，不能把缺失当 0。任务提交记录本次 HTTP 和逻辑重试，不把后台任务完成并入 HTTP 时间线。
- 每请求最多 96 个阶段、64 次详细尝试、每次 16 个 HTTP 交换、每交换 64 个网络事件且全请求最多 512 个网络事件；真实尝试计数仍保留。正文外元数据有长度限制，超限或裁剪均标记 partial/truncated。JSON 超过 64 KiB 时先裁剪网络事件，再裁剪交换详情，摘要保留。

请求最终结果以最后一次逻辑尝试为依据；已恢复的重试失败不把最终成功改成失败，panic 和入站上下文的取消/超时优先。原始网络错误在脱敏前分类：响应头前使用 request_timeout/request_canceled，响应体读取阶段使用 read_timeout/read_canceled；这些是 trace_data 中开放字符串的新增值，不改变数据库列或载荷版本。

前端只根据实际观测画区间。重复网络回调无法唯一配对时保留原始事件；提前响应产生的反向区间不绘制；未观测到的连接复用状态及阶段结束保持未知。阶段可能重叠或存在间隙，不能把所有阶段相加解释为总耗时。

### 写入、保留及配置

请求终态冻结并序列化后，摘要及原始 JSON 字节经 512 条有界内存队列写入，最多每批 64 条且实际入库文本总大小不超过 1 MiB；低负载由 250ms 定时器刷新，有积压时优先处理队列并凑满批次。慢 INSERT 后积压的 tick 不触发小批次写入，避免写库限速时额外拉长排空时间。原始 JSON 仍受 64 KiB 上限约束；关系型日志库的应用压缩在已有异步写入协程执行，ClickHouse 直接提交原文，不增加同步请求路径的压缩工作。每次写库使用独立 3 秒超时，仅暂时性错误最多尝试 3 次并带退避和抖动。队列满、JSON 编码失败、最终写库失败都有计数和诊断日志，不能保证异常退出或数据库故障时每条记录不丢。

| 环境变量 | 默认值 | 行为 |
| --- | --- | --- |
| REQUEST_TRACE_ENABLED | true | 是否采集中转请求；关闭后仍能查询保留记录 |
| REQUEST_TRACE_RETENTION_DAYS | 7 | 1–3650 天；关系库由 master 分批清理，有积压时续跑，ClickHouse 使用 TTL |

系统设置 → 运维设置 → 日志维护提供“请求时间线压缩”选项，适用于关系型日志库，沿用现有系统设置接口及权限，持久化键为 `request_trace.compression_level`。默认 `fastest`，允许 `fastest`、`default`、`better`、`best` 四档，分别对应当前 Go 库的 `SpeedFastest`、`SpeedDefault`、`SpeedBetterCompression`、`SpeedBestCompression`。服务端在写入配置前校验枚举，配置事务提交成功后更新内存；其他节点沿用已有选项同步周期。修改后，使用关系型日志库的节点后续出队记录采用新档位，无需重启，不重写历史记录；ClickHouse 不读取该档位。

关系型日志库每条记录使用独立 Zstd 帧并启用校验和，不使用跨请求字典；写入协程只持有一个单并发编码器及可复用缓冲区，切换档位时释放旧编码器。压缩帧转为标准 Base64 后使用以下 JSON 封装，`raw_bytes` 为解压前原始 JSON 的 UTF-8 字节数：

```json
{"codec":"zstd-base64","raw_bytes":1544,"payload":"..."}
```

只有完整封装文本比原始 JSON 更小时才保存压缩形式；压缩失败记录诊断并保留原始 JSON。压缩不会删除阶段、精度或其他字段，原有采集上限和裁剪规则保持不变。读取时自动识别历史原始 JSON 与压缩封装，严格校验 Base64、Zstd 校验和、解压大小及 `raw_bytes`，解压输出和窗口最多 64 KiB。损坏或不支持的载荷保留摘要，并返回现有 `invalid_data` 详情状态。普通用户只读取摘要，不需要解压。

`schema_version` 仍表示解压后的时间线 JSON 版本，压缩格式由 `codec` 标识，不增加或删除数据库列。所有档位均可互相读取。尚未接入解压的旧版服务只能展示压缩记录的摘要，多节点部署及回滚时需确保处理详情查询的节点具备解码支持。

正常关停先等待 HTTP 请求，再限时排空追踪队列并停止清理协程，最后关闭数据库。队列是进程内数据，节点异常退出存在丢失窗口；完成后异步落库也存在短暂可见性延迟。在主节点完成建表后再启动依赖新表的其他节点。

## 1. 背景与目标

现有用量日志能回答"谁、用哪个模型、走哪个渠道、花了多少、报了什么错"，但几乎不记录请求和响应本身的形状，并且相当一部分失败请求不进 `logs` 表。排查问题时经常只有一句错误消息。

目标：

1. 每条请求日志附带足够定位问题的元数据：大小、状态、毫秒级耗时、结束原因、请求形状统计、上游返回的关键标识。
2. 未到达渠道的失败也能在日志页按请求 ID 查到。
3. 不保存请求体和响应体正文。
4. 不改 `logs` 表结构，不新增表。
5. 对热路径的开销可忽略，存储增量可通过开关控制。

## 2. 非目标

- 不保存请求体、响应体正文或其片段。唯一的原文是失败时上游返回的错误响应体（见 4.4）。
- 不保存上游响应头（限流头、`retry-after`、`cf-ray` 等）。
- 不给用量日志列表加列，不加筛选项，不做基于这些字段的统计报表。
- 不覆盖异步任务（视频生成、Midjourney 等）的提交与轮询日志。这条路径本次未分析。
- 不覆盖 Realtime WebSocket 的响应字节统计。
- 不引入独立追踪表、对象存储或采样系统。

## 4. 数据设计

所有新增字段都写在 `logs.other` 里，分三处：`other.trace`（用户可见）、`other.admin_info.trace`（管理员）、`other.root_info`（Root）。字段名为提案。

通用规则：

- 取不到或为零的可选项不写入，前端也不显示对应的行。例外是消息条数，为 0 时也保存。
- 整个子对象为空时省略该键。
- 旧日志没有这些字段，前端按"有才显示"渲染，不需要回填。

### 4.1 用户可见：`other.trace`

| 字段 | 类型 | 含义 | 何时写入 |

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `upstream_error_body` | string | 上游错误响应体原文，截断到 4096 字节，写入前经 `common.MaskCredentials` 脱敏 |
| `upstream_error_body_truncated` | bool | 是否被截断 |

只在失败记录上保存，受单独的开关控制。它的内容是供应商的报错文本，不含用户的提示词。前端沿用现有的"Root 诊断"分区展示。

### 4.5 明确不保存的内容

- 请求体与响应体正文，包括截断片段。
- 令牌和渠道密钥。
- 终端用户标识（OpenAI 的 `user`、Claude 的 `metadata.user_id`）。
- 工具定义、工具调用参数。
- 多媒体的地址和数据。
- 上游响应头。

### 4.6 修正：识别 Anthropic 的上游请求 ID

`relay/channel/api_request.go:552` 和 `service/http.go:28` 在 `X-Oneapi-Request-Id`、`X-Request-Id` 之外补充识别 `request-id`，写入现有的 `upstream_request_id` 列。这是独立的缺陷修复，不受追踪级别控制。

## 5. 未到达渠道的失败落库

这类失败写成一条普通的错误日志，全部使用 `logs` 表现有的列，不改表结构。

| 现有列 | 填什么 |
| --- | --- |
| `type` | 5，现有的"错误"类型 |
| `user_id`、`username`、`token_id`、`token_name` | 已鉴权的填实际值；未鉴权的填 0 和空串 |
| `model_name` | 能解析出来就填，否则为空 |
| `channel` | 0 |
| `quota`、`prompt_tokens`、`completion_tokens` | 0 |
| `request_id` | 返回给客户端的请求 ID |
| `content` | 错误消息，经 `common.MaskCredentials` 脱敏 |
| `ip` | 已鉴权的沿用"用户是否开启记录 IP"；未鉴权的直接记录来源 IP |
| `other` | `status_code`、`error_code`、`error_type`、`request_path`，以及 4.1、4.2 中能取到的字段 |

按能否归属到用户分两档，各配开关：

| 档位 | 包含 | 默认 | 理由 |
| --- | --- | --- | --- |
| 已鉴权的失败 | 请求校验失败、无可用渠道、用户限流、敏感词、计价错误 | 开 | 能归属到用户和令牌，数量受用户自身请求量约束 |
| 未鉴权的失败 | 令牌无效、IP 限流 | 关 | 不属于任何用户，被扫描时量可能很大 |

额度不足（403）默认仍不记录：余额耗尽的用户持续重试时每次都会写一行。待确认是否需要单独开关放开。

对用户侧的影响：

- 用户会在自己的日志页看到已鉴权的失败记录。
- 未鉴权的记录 `user_id` 为 0，不属于任何用户，只有管理员和 Root 能看到。
- 用量、RPM、TPM 统计只查 `type = 2` 的消费记录（`model/log.go:680`、`model/log.go:722`），不受新增错误行影响。

所有错误日志仍受现有的 `ERROR_LOG_ENABLED` 总开关约束：它关闭时，本节的记录同样不写。

## 7. 后端实现要点

### 7.1 采集点

| 数据 | 采集位置 | 说明 |
| --- | --- | --- |
| `trace.ms` | 上下文里已有的请求开始时间 | `processChannelError` 已在用同一个时间点 |
| `trace.req_bytes` | `common.GetBodyStorage(c).Size()` | 请求体已缓存，取大小是常数时间 |
| `client.*` | 请求进入时的请求头 | 解压中间件会删除 `Content-Encoding` 头（`middleware/gzip.go:91`），必须在它之前或之内记下 |
| `trace.resp_bytes` | gin 的 `c.Writer.Size()` | 流式时包含保活的 ping 帧；未写出任何内容时返回 -1，需按 0 处理 |
| `attempt` | `RelayInfo.RetryIndex` | 已存在 |
| `upstream.status` / `proto` / `header_ms` / `req_bytes` | `relay/channel/api_request.go:532` 的 `doRequest` | 所有走通用请求路径的渠道一处覆盖 |
| `shape.*` | 各请求 DTO | 见 7.2 |
| `shape.keys` | 请求校验失败的返回处 | 见 7.3 |
| `finish_reason`、`resp.*` | 各协议的流式与非流式响应处理 | 见 7.4 |
| `upstream_error_body`、`upstream.error_type` | `service/error.go:87` 的 `RelayErrorHandler` | 见 7.5 |

采集结果挂在 `RelayInfo` 上的一个追踪结构里，在生成日志 `other` 时写入。成功日志的入口是 `service/log_info_generate.go` 的 `GenerateTextOtherInfo`，错误日志的入口是 `controller/relay.go` 的 `processChannelError`，两处共用同一个写入函数，由它按级别决定写哪些层。

### 7.2 请求形状的轻量计数

现有的 `TokenCountMeta` 已包含消息数、工具数和文件列表，但只有在开启 token 统计或敏感词检查时才完整生成；其余情况走只取 `max_tokens` 的快速路径（`controller/relay.go:136`）。完整生成会拼接全部文本，开销不小。

需要为每种请求 DTO 提供一个只计数、不拼接文本的方法：遍历消息累加文本长度并按类型数多媒体个数。它的成本与消息条数成正比，不复制内容。级别为 `off` 时不调用；级别为 `errors` 时只在写错误日志时调用。

### 7.3 顶层字段名

只在请求校验失败时执行：把请求体解析成"字段名到原始值"的映射后只取键。约束：

- 请求体超过 1 MiB 时跳过。
- 最多保存 32 个字段名，每个最长 64 字符。
- 解析失败时不写入该字段。
- JSON 解析必须走 `common/json.go` 的封装。

### 7.4 结束原因与响应统计

这是改动面最大的一项：OpenAI 兼容、Claude、Gemini、Responses 四种协议各有流式和非流式两条处理路径，需要在各自解析响应的位置把结束原因、响应 ID、实际模型、选项数、工具调用数写到追踪结构上。部分位置已经在读取这些值（例如 `relay/channel/claude/relay-claude.go:97`、`relay/channel/gemini/relay-gemini.go:257`），只需顺手记录。

回复字符数优先复用流式处理中已有的累计文本；没有累计的路径按分片累加长度。实现时需逐条路径确认。

未覆盖到的渠道适配器保持字段缺省，前端不显示对应的行，不影响其他功能。

### 7.5 上游错误原文

`RelayErrorHandler` 已经读入完整的错误响应体。在这里截取前 4096 字节，随错误对象带回 `processChannelError`，经 `common.MaskCredentials`（传入当前渠道密钥）脱敏后写入 `root_info`。

`NewAPIError` 定义在 `relaykit/types/error.go:90`。给它加载体属于 `relaykit` 的公开接口变更，必须按项目规则单独验证：

```bash
cd relaykit && GOWORK=off go build ./...
```

### 7.6 未到达渠道的失败

- 中间件的统一拦截点 `abortWithOpenAiMessage`（`middleware/utils.go:14`）里补一次错误日志写入。鉴权、限流、渠道分发三个中间件在入口处各自标记当前阶段，拦截点读取后写入 `trace.stage`。
- 全局与 IP 限流没有走这个拦截点（`middleware/rate-limit.go:143`），需要单独补调用。
- `controller/relay.go` 里进入重试循环之前的几处提前返回（`:115`、`:142`、`:159`）和循环内选不到渠道的分支（`:200`）补调用。
- 是否已鉴权按上下文里是否有用户 ID 判断。
- 每个请求最多写一条这类记录。
- 未鉴权档按来源 IP 做每分钟限量，超出后丢弃并在本地日志计数。限量值待确认，建议每 IP 每分钟 10 条。

记录令牌无效这类事件属于认证审计。按 `AGENTS.md` 的认证安全要求，实现前需阅读 OWASP 的认证与会话管理速查表，并确保记录里不含令牌本身。本设计不保存 `Authorization` 头的任何部分。

## 9. 性能与容量

以下为根据代码和原型示例数据的推算，未做压测。

每条日志 `other` 的 JSON 字节数：

| 记录 | 现在 | 级别 `all` | 加上游错误原文 |
| --- | --- | --- | --- |
| 非流式成功 | 148 | 755 | — |
| 流式成功 | 236 | 764 | — |
| 限流错误 | 156 | 528 | 859 |
| 校验失败 | 117 | 366 | — |

"现在"一列省略了部分计费字段，真实值更大，但增量是准的：级别 `all` 每条约多 400 到 600 字节，级别 `errors` 的成功日志约多 80 字节。上游错误原文最坏 4 KB，只出现在失败记录上。

| 环节 | 影响 |
| --- | --- |
| 写入 | 每个请求仍只写一条日志，写入发生在响应返回之后（`model/log.go:103`），不影响用户感知的延迟 |
| 列表查询 | 筛选和排序都走已有索引列，不读 `other`；每页多返回几十 KB |
| 统计查询 | MySQL 和 PostgreSQL 里行变宽后，按时间范围扫描的统计查询会按行宽增长的比例变慢；ClickHouse 是列存，不受影响 |
| 行数 | 未到达渠道的失败落库会增加行数，对表和每个索引都有成本，影响大于行宽 |

按级别 `all` 估算：每天 10 万条日志约多 50 MB，每天 100 万条约多 500 MB。

## 10. 兼容性与约束

- **数据库**：不改表结构，SQLite、MySQL、PostgreSQL、ClickHouse 都不需要迁移。`other` 是未限长的文本列。按项目规则这类改动不触发三库迁移验证，但仍需在三种关系库上各跑一次写入与读取，确认 JSON 文本往返无损。
- **新旧节点混跑**：旧节点读到新日志时，未知字段随所在层一起被保留或裁剪，行为正确。旧前端忽略未知字段。
- **旧日志**：没有追踪字段，前端各分区不渲染，无需回填。
- **`relaykit` 独立性**：7.5 涉及 `relaykit` 公开类型，需单独构建验证。
- **JSON**：所有序列化与反序列化走 `common/json.go` 的封装。
- **回退**：把级别设为 `off` 即恢复现有行为；已写入的追踪字段留在历史日志里，不影响任何功能。

## 11. 测试计划

后端，优先扩展现有测试文件，新增测试文件不超过一个：

- 追踪结构到 `other` 的写入：三种级别 × 成功与失败，断言各层出现的字段；零值与空对象省略。
- 身份裁剪：用户看不到 `admin_info.trace` 和 `root_info`，管理员看不到 `root_info`。
- 上游错误原文：超过 4096 字节被截断并置标记；渠道密钥被脱敏；开关关闭时不写。
- 未到达渠道的失败：两档开关各自生效；`ERROR_LOG_ENABLED` 关闭时不写；每个请求最多一条；未鉴权档的 IP 限量。
- 请求形状计数：四种协议各一个带多媒体与工具的请求，断言各项个数；不含的项不出现。
- 顶层字段名：拼错的必填字段出现在列表里；超过大小上限时跳过；损坏的 JSON 不写入。
- 上游请求 ID：响应头为 `request-id` 时被识别，且优先级低于 `X-Oneapi-Request-Id`。

前端见 8.4。完成前执行 `bun run typecheck`、涉及文件的 lint，以及受影响的测试文件。

## 12. 实施拆分

按可独立提交、独立验证的顺序：

1. 设置项与追踪结构；写入无需解析响应即可得到的字段（耗时、请求体大小、响应体大小、客户端信息、尝试序号、上游状态与协议、响应头耗时）；三种级别。
2. 请求形状的轻量计数；校验失败时的顶层字段名。
3. 各协议的结束原因与响应统计。
4. 上游错误原文与上游错误类型；Anthropic 上游请求 ID 的识别。
5. 未到达渠道的失败落库与两档开关。
6. 前端：类型、详情弹窗分区、后台设置、七种语言、测试。

第 3 步改动面最大，可以按协议拆成多次提交。第 4 步里的上游请求 ID 识别是独立修正，可以提前单独合入。

## 13. 讨论中已确定的决定

- 请求体和响应体正文不保存，也不保存截断片段。
- 失败时只保留上游错误原文；请求侧用顶层字段名列表代替请求体片段。
- 上游响应头整组不保存。
- 列表不加列；耗时沿用现有的列，请求与响应大小、结束原因只在详情里显示。
- 详情弹窗沿用现有布局与组件，只增加分区和行。
- 图片、工具、视频等统计项没有时不保存、不显示。
- 全部新增字段放在 `logs.other`，不改表。
- 未到达渠道的失败用现有的列写成错误日志。

## 14. 待确认

1. 请求追踪级别的默认值。取决于日请求量和日志库类型：量小或使用 ClickHouse 可以默认 `all`；每天百万级且使用 MySQL 或 PostgreSQL 建议 `errors`。
2. 额度不足（403）是否需要一个单独的开关放开记录。
3. 未鉴权档的每 IP 每分钟限量值。
4. 详情弹窗里重试的逐次尝试，是按请求 ID 再查一次，还是只显示当前这一条。
5. 请求头白名单是否保留 `anthropic-version` 等三项。
6. 在哪个分支上实现：沿用当前分支，或按既有约定新开 `custom/rc35-request-trace`。

## 15. 风险

- **各渠道适配器覆盖不全**：结束原因和响应统计依赖各协议的处理代码，冷门渠道可能缺字段。缓解：字段缺省时前端不显示，不阻塞其他功能。
- **`resp_bytes` 不等于上游响应大小**：它是写回客户端的字节数，经过格式转换后与上游原始大小不同，流式时还包含保活帧。文案上写"响应体大小"时需在提示里说明口径。
- **未鉴权日志被刷量**：依赖默认关闭和按 IP 限量。开启前应确认日志清理策略。
- **统计查询变慢**：行变宽对 MySQL 和 PostgreSQL 的范围统计有影响，上线后需观察；必要时把级别降到 `errors`。
- **上游错误原文里的敏感信息**：部分上游会在错误体里回显请求片段或账号标识。缓解：仅 Root 可见、凭证脱敏、可整体关闭。脱敏只覆盖凭证，不覆盖回显的用户内容。
