# 用户模型折扣功能人工全链路测试清单

## 1. 测试目的与范围

本清单用于在测试环境中人工验证“用户模型折扣”从管理配置、独立存储、缓存读取，到普通请求计费、异步任务结算、余额扣减、日志和渠道统计的完整链路。

当前实现的关键口径：

- 折扣规则存储在 `user_model_pricings`，版本存储在 `user_model_pricing_revisions`，不读取旧的 `users.setting` 折扣字段。
- 折扣以基点保存：`10000` 表示 100% 原价，`8000` 表示按原价的 80% 计费，`1` 表示 0.01%。未配置规则按 100% 计费。
- 100% 原价不会保存为独立折扣规则；清除全部规则后仍保留可用于并发校验的版本。
- 用户和令牌承担折后费用；渠道 `used_quota` 记录折扣前的站内费用。
- 普通消费日志记录折前、折后和优惠金额；异步任务的调整日志必须标明任务总额口径。
- 已开始的请求或任务使用取得时的折扣快照；保存新规则只影响之后取得快照的请求。

本清单不包含压测、QPS 测试、持续并发测试、每天 600 万条数据的容量测试或性能阈值结论。缓存部分只做顺序单请求、双会话和故障恢复验证，不以单次耗时推导性能结论。

### 1.2 测试设计方法

每条用例都应先确定需求/风险、前置状态、输入等价类、边界值、操作步骤、可观察结果和证据，再执行。测试结果必须能回答“哪条规则、哪个用户、哪个请求或任务、哪一笔金额被验证”。

#### 等价类和边界值

对每个输入域至少选择一个正常类、一个异常类和边界值；同类输入不需要机械重复所有值。

| 输入或状态域 | 有效等价类 | 无效等价类 | 必测边界 |
| --- | --- | --- | --- |
| `discount_bps` | 1-9999 的折扣、10000 原价 | 空、非数字、0、负数、大于 10000、NaN/Infinity | 1、2、9999、10000、10001 |
| `revision` | 当前正版本且在前端安全整数范围内 | 缺失、0、负数、字符串、旧版本、超安全整数 | 1、当前版本、当前版本-1、超界值 |
| 模型名 | 已启用模型、别名、修饰符、停用后保留规则 | 空白、超长、归一化后重复 | 去空格、大小写、别名归一化前后 |
| 规则数量 | 0、1、1000 条有效规则 | 1001 条请求或完整规则集超限 | 0、1、999、1000、1001 |
| 抽屉分页 | 第 1 页、恰好 20 条、超过 20 条 | 非法页码、超过最大页码 | 0、1、19、20、21、最后一页、最后一页之后 |
| 权限关系 | 可管理的低级目标 | 未登录、同级、上级、已删除目标 | 角色边界前后各一个目标 |
| 任务终态 | 最终金额低于、等于、高于预扣 | 失败、超时、快照损坏、重复终态 | 三种差额为 0、正数和负数 |

#### 决策表

对会同时影响结果的条件组合至少执行一次，不用只测试每个条件单独成立的情况。最低组合如下：

| 决策主题 | 条件组合 | 预期动作 |
| --- | --- | --- |
| 保存规则 | 有权限 + 当前 revision + 合法规则 | 原子保存并递增 revision |
| 保存规则 | 有权限 + 旧 revision | HTTP 409，原规则和草稿不被覆盖 |
| 保存规则 | 无权限 + 任意 revision | 拒绝且不泄漏目标规则 |
| 读取折扣 | Redis 命中/未命中/丢键 + 数据库正常 | 最终使用数据库权威版本，不把缺失解释成原价 |
| 读取折扣 | Redis 异常 + 数据库正常/异常 | 数据库正常时回源；数据库异常时明确失败 |
| 普通结算 | 无规则/100%/小于 100% | 分别验证原价、无优惠和折后费用 |
| 任务结算 | 提交后未改价/已改价 + 成功/失败 | 使用提交快照，分别执行结算或补偿 |
| 任务差额 | 最终金额小于/等于/大于预扣 | 分别退款、无动作或补扣；用户和渠道使用各自口径 |

#### 状态转换

用状态转换验证事件顺序和非法跳转，而不是只验证最终页面文字：

- 规则状态：无规则 -> 读取版本 -> 编辑草稿 -> 保存中 -> 已提交新版本 -> 缓存过期/淘汰 -> 删除或再次保存。每次转换都核对数据库、revision、缓存和页面。
- 任务状态：创建/预扣 -> 已提交 -> 处理中 -> 成功或失败 -> 结算/退款。重复轮询、改价、重启和上游异常都要确认不会跳过快照或重复结算。
- 请求状态：鉴权 -> 取得折扣快照 -> 上游调用 -> 实际用量 -> 预扣/结算 -> 日志。任何一步失败都要验证错误可见和补偿方向。

#### 预期结果和证据

- 每个计费用例必须同时观察用户/令牌额度、渠道 `used_quota`、消费或任务日志，不能只看 HTTP 200。
- 每个权限用例必须同时验证响应状态、响应内容、数据库是否变化和目标用户是否收到影响。
- 每个缓存用例必须记录规则 revision、折扣值、请求/任务 ID 和缓存/数据库状态；不以“等待 TTL”作为唯一证据。
- 失败用例要区分产品拒绝、上游失败、数据库失败和缓存故障，不把错误页面显示出来误判成账务已补偿。

### 1.3 人工执行约束

- 使用固定的少量测试数据和可复现的上游响应；一条用例尽量只触发一个请求或一个任务。
- 需要验证在途快照时，仅使用一个可控延迟的测试上游请求，不启动并发循环、不做持续运行、不统计吞吐。
- 每个阶段执行前恢复本阶段前置数据，阶段结束保存证据；发现 P0/P1 后先停止继续扩大数据影响并记录复现状态。
- 对不适用的入口标记 `N/A` 并写明原因；不能用“当前没有渠道/没有任务”替代适用链路的验证。

## 3. 测试准备

### 3.1 账号和权限

本清单的执行账号只使用普通管理员权限，不设置或依赖 `root` 角色。准备以下测试账号，角色名称按当前系统的角色定义填写：

| 标识 | 用途 | 要求 |
| --- | --- | --- |
| `ADMIN-OPERATOR` | 普通管理员 | 只能管理权限范围内的低级目标用户 |
| `PEER-OPERATOR` | 同级管理员 | 用于验证同级用户不能管理彼此 |
| `USER-A` | 目标用户 A | 配置多个模型折扣 |
| `USER-B` | 目标用户 B | 配置与 A 相同模型但不同折扣 |
| `USER-C` | 无折扣用户 | 验证默认原价和无跨用户污染 |
| `DELETED-USER` | 删除边界 | 在隔离测试库中创建后删除 |

要求：

- `USER-A` 和 `USER-B` 的分组、角色至少有一项不同，且两人都配置同一个模型，便于验证总览不能把相同模型的两名用户合并。
- `ADMIN-OPERATOR` 准备一个可管理目标和一个不可管理目标；不可管理目标覆盖同级、上级、封禁或已撤销权限等实际边界。
- 所有账号使用临时测试凭证。测试记录不得包含密码、Access Key、私钥或完整 JWT。

### 3.2 模型、分组和渠道

准备能在测试环境稳定返回固定用量的渠道或测试上游，并建立以下模型目录：

| 标识 | 用途 | 配置要求 |
| --- | --- | --- |
| `M-RATIO` | 普通倍率模型 | 有确定的输入/输出价格和分组倍率 |
| `M-FIXED` | 固定价格模型 | 有确定的固定费用 |
| `M-TIERED` | 阶梯或表达式计费模型 | 能产生跨档位的可核对用量 |
| `M-ALIAS` | 计费别名/修饰符模型 | 覆盖显式别名、`@` 修饰符或既有特殊匹配规则 |
| `M-DEFAULT-GROUP` | 默认分组模型 | 在 `default` 分组启用 |
| `M-VIP-GROUP` | 其他分组模型 | 只在 `vip` 或其他分组启用 |
| `M-DISABLED` | 停用模型 | 先配置规则，再停用能力 |

模型准备要求：

- `M-DEFAULT-GROUP` 和 `M-VIP-GROUP` 必须来自不同分组，确认编辑目录取全部分组的启用模型，而不是操作者或目标用户当前分组的模型。
- 至少有一个模型在多个渠道重复出现，验证展示去重和计费身份归一化。
- 记录每个模型的原始计费价格、分组倍率、渠道映射、实际输入/输出用量和系统既有取整规则。
- 为 `USER-A` 准备足够钱包额度、令牌额度和订阅状态；另准备余额刚好不足折前但足够折后的边界账号。
- `USER-A`、`USER-B` 使用相同模型的规则分别设置为例如 80% 和 60%，`USER-C` 不设置规则。

### 3.3 基线快照

在写入折扣前保存：

- 三名用户的钱包额度、令牌剩余额度、订阅状态和分组。
- 相关渠道的 `used_quota`、请求成功数和失败数。
- 用户日志、任务日志、任务 `private_data`/`properties` 中与金额相关的原始状态。
- `user_model_pricings` 和 `user_model_pricing_revisions` 的行数及目标用户记录。
- Redis 是否启用，以及测试用户的折扣缓存是否为空、命中或已过期。

所有计费对比尽量使用同一模型、同一请求内容和可复现的上游用量；若上游用量不能固定，以日志中的同一次实际用量重新计算，不直接比较两次可能不同的请求总额。

## 4. 数据表和初始化

- [ ] **DB-01 独立表创建**：在包含真实用户、任务和日志的隔离数据库上启动服务，确认创建 `user_model_pricings` 和 `user_model_pricing_revisions`，原有表行数、列和关键数据未改变。
- [ ] **DB-02 重复启动**：停止并重新启动服务两次，确认没有重复 DDL、重复版本行或启动报错。
- [ ] **DB-03 空规则初始化**：读取一个从未配置折扣的用户，确认返回空 `items`、正 `revision` 和启用模型目录；不返回伪造的旧折扣。
- [ ] **DB-04 版本稳定**：重复读取同一用户，确认没有规则变更时 `revision` 不变化，空规则也有稳定版本。
- [ ] **DB-05 原价不落表**：提交 100% 规则后，确认接口可按原价工作，但 `user_model_pricings` 不保存该模型的有效折扣行。
- [ ] **DB-06 清空规则**：提交空 `items`，确认目标用户所有独立折扣规则删除、版本递增、后续计费恢复 100%，且不删除其他用户规则。
- [ ] **DB-07 停用模型保留**：先为模型配置折扣，再停用该模型，确认独立表规则不因目录隐藏而被无意删除；重新编辑并保存其他启用模型后，该隐藏规则仍按产品约定保留或被明确提示处理。
- [ ] **DB-08 用户删除清理**：在隔离库删除目标用户，确认规则、版本和缓存不会留下可被新用户 ID 复用的有效折扣，也不会复活已删除用户。
- [ ] **DB-09 旧数据兼容**：数据库中预置旧用户、旧任务和旧日志后启用功能，确认不执行旧折扣数据迁移，不新增 `tasks`/`logs` 费用列，不读取 `users.setting` 中的旧折扣字段。

## 5. 权限和 API

以下接口均使用真实鉴权请求验证，不只在浏览器中观察页面：

- `GET /api/user/:id/model-pricing`
- `PUT /api/user/:id/model-pricing`
- `GET /api/user/model-pricing?summary=true`
- `GET /api/user/:id/model-pricing/rules?p=1`

### 5.1 访问控制

- [ ] **API-01 未登录访问**：四类接口均被认证中间件拒绝，不返回用户规则、revision、模型名或摘要数据。
- [ ] **API-02 目标用户权限**：`ADMIN-OPERATOR` 读取和修改可管理目标成功；读取和修改同级、上级或无权限目标均失败，且响应不泄漏规则内容。
- [ ] **API-03 普通管理员总览范围**：`ADMIN-OPERATOR` 打开用户折扣总览时，只能看到其权限范围内的目标用户；同级、上级或无权限用户的规则不会出现在总览、摘要或抽屉中。
- [ ] **API-04 删除目标**：目标用户不存在、已删除或 ID 非法时，GET、PUT 和规则分页接口均返回明确错误，不创建版本行。
- [ ] **API-05 只读接口不改账**：GET 总览、详情和规则分页前后，钱包、令牌、渠道金额、任务和日志均无变化。

### 5.2 读取接口

- [ ] **API-06 详情结构**：详情返回 `user_id`、`items`、`revision`、`model_names`；规则模型名与折扣基点正确，排序稳定。
- [ ] **API-07 全部分组模型**：详情的 `model_names` 包含所有分组的启用模型，去除重复计费身份；不因操作者或目标用户分组过滤。
- [ ] **API-08 只显示启用目录**：新增或停用渠道能力后重新读取，目录反映启用状态；已有规则的保留行为与 DB-07 一致。
- [ ] **API-09 用户总览摘要**：`summary=true` 返回按用户聚合的 `items`、`total`、`page`、`page_size`、`total_rules`、`total_models`，同一用户不重复成多行。
- [ ] **API-10 相同模型的多个用户**：`USER-A` 和 `USER-B` 配置同一模型时，总览返回两条用户记录，各自的折扣和 `rule_count` 正确。
- [ ] **API-11 关键字范围**：关键字匹配用户名、显示名、邮箱或模型名；模型关键字只让匹配模型出现在明细/预览中，不把该用户其他模型错误扩展进结果。
- [ ] **API-12 分组筛选**：`group=vip` 与 `group=default` 分别只返回对应用户；清空分组后恢复完整范围。
- [ ] **API-13 角色筛选**：`role=<实际角色值>` 只返回对应角色；页面和响应不把账号启用状态当作该页的筛选维度。
- [ ] **API-14 分页边界**：第一页、最后一页、超过总页数、空结果和 `page_size` 边界均返回稳定空数组或正确数据，不重复用户。
- [ ] **API-15 抽屉规则分页**：规则接口每页最多 20 条，`total` 与筛选后的规则数一致；按页读取不会丢失、重复或跨用户读取规则。
- [ ] **API-16 抽屉关键字**：规则页按模型关键字只返回匹配规则；按该用户的用户名/邮箱命中时，规则范围符合当前接口约定且不扩展到其他用户。

### 5.3 写入接口和校验

使用当前 GET 返回的 `revision`，每个请求都验证数据库、缓存和后续计费结果。

- [ ] **API-17 正常替换**：提交多个模型的 80%、60%、95% 规则，返回新 revision；旧规则被完整替换，不产生重复行。
- [ ] **API-18 完整替换语义**：PUT 只保留请求中的有效规则；明确测试“保留规则、修改规则、删除规则”三种组合，确认不是增量追加。
- [ ] **API-19 缺少 revision**：缺少 `revision`、`revision=0`、负数或非法类型均被拒绝，原规则、余额和缓存不变。
- [ ] **API-20 版本冲突**：两个管理页面读取同一 revision，先保存一页，再用旧 revision 保存另一页；后一次返回 HTTP 409/`USER_MODEL_PRICING_CONFLICT`，不能覆盖先保存的规则，前端草稿保留。
- [ ] **API-21 折扣下界**：`discount_bps=1` 成功；`0`、负数和空值失败，不能被当作免费或自动恢复原价。
- [ ] **API-22 折扣上界**：`discount_bps=10000` 成功但不落有效规则；大于 10000 失败。
- [ ] **API-23 小数精度**：使用界面输入 0.01%、33.33%、99.99% 后，接口基点分别为 1、3333、9999；不能出现浮点误差造成额外一倍或少一位。
- [ ] **API-24 模型名校验**：空白模型名、去除空格后为空、超过 128 字节的模型名均失败；原规则不变。
- [ ] **API-25 模型归一化**：对大小写、空格、别名、思考模型和 Gizmo 等实际匹配形式分别提交，确认保存、管理展示和计费查找使用同一计费身份。
- [ ] **API-26 归一化重复**：提交归一化后相同的两个别名规则，确认明确失败，不能静默覆盖其中一条。
- [ ] **API-27 数量上限**：有效折扣规则超过 1000 条时整批失败；包含界面不可见的已保留规则时也按完整规则集计数，不能部分写入。
- [ ] **API-28 原子失败**：在校验失败、版本冲突或数据库约束失败后，确认不存在“版本已递增但规则未换完”“部分新规则已写入”的半套状态。
- [ ] **API-29 审计记录**：成功修改产生目标用户管理审计；失败请求不伪造成功审计，审计中的 revision 和 rule count 与实际一致。

### 5.4 安全和输入验证

以下用例按 OWASP WSTG 的授权、IDOR、权限提升、输入校验、错误处理和 API 测试思路执行。所有操作只在隔离测试环境中进行，测试账号仍只有普通管理员权限。

- [ ] **SEC-01 水平越权/IDOR**：把 URL 中的目标用户 ID 从可管理的 `USER-A` 改为同级或其他用户 ID，分别调用 GET、PUT 和规则分页接口；请求被拒绝，规则、revision、余额和审计不发生越权变化。
- [ ] **SEC-02 垂直越权**：使用普通管理员访问更高权限用户或管理员目标，验证页面入口、详情接口、规则分页和保存接口都执行服务端权限校验，不能只依赖前端隐藏按钮。
- [ ] **SEC-03 越权修改确认**：即使攻击者知道合法 `revision` 并构造完整 `items`，也不能修改无权限目标；失败响应不返回其规则数量、模型名或折扣。
- [ ] **SEC-04 会话撤销**：登录后取得页面和接口凭证，注销、封禁或撤销该会话，再调用详情、总览和 PUT；服务端拒绝旧凭证，不因浏览器缓存继续显示可操作成功。
- [ ] **SEC-05 方法和内容类型**：对只允许 GET/PUT 的接口尝试错误 HTTP 方法、缺少或错误 `Content-Type`、空 body 和重复请求体，确认不触发意外写入，不返回成功样式响应。
- [ ] **SEC-06 质量赋值边界**：在 PUT body 中额外加入 `user_id`、`role`、`quota`、`status` 等字段，确认不能修改目标用户身份、权限、余额或状态；服务端只处理规定字段。
- [ ] **SEC-07 查询输入安全**：在 `keyword`、`group`、`role`、模型名和显示名中使用引号、通配符、Unicode、控制字符和超长字符串，确认参数被正确处理，不出现 SQL 错误、跨用户结果、堆栈或服务端崩溃。
- [ ] **SEC-08 模型名语法**：使用前后空格、别名、分隔符、大小写、反斜杠和 JSON 特殊字符，确认归一化、存储、日志和响应不会改变到另一用户或另一模型规则。
- [ ] **SEC-09 错误信息隔离**：制造 400、401/403、404、409、数据库错误和 Redis 错误，确认响应不包含 SQL、Redis 地址、内部堆栈、令牌、密钥或无权限用户数据。
- [ ] **SEC-10 伪造操作者身份**：修改请求头、body 或查询参数中的用户标识，确认审计操作者、目标用户和实际登录身份均由服务端上下文决定，不能由客户端伪造。
- [ ] **SEC-11 Cookie 会话防跨站请求**：若部署使用 Cookie 鉴权，使用隔离站点发起跨站 PUT 验证 CSRF 防护；若仅使用 Bearer 鉴权，记录为 `N/A` 及其依据。

## 7. 缓存和快照一致性

这些用例只验证正确性，不做循环并发或吞吐测试。Redis 操作必须在隔离实例执行。

- [ ] **CACHE-01 冷缓存读取**：清理测试用户的本地/Redis 折扣缓存后发起请求，结果来自数据库权威规则，首次请求不误判为原价。
- [ ] **CACHE-02 热缓存读取**：同一用户连续发起两次顺序请求，第二次使用相同正确规则；用户 A 的缓存不会被用户 B 命中。
- [ ] **CACHE-03 同模型跨用户隔离**：A 为同一模型设置 80%，B 设置 60%，交替请求 A、B、A、B，四次分别使用各自折扣。
- [ ] **CACHE-04 改价后新读**：保存 80% 到 60% 后，新取得快照的请求使用 60%，不受旧 TTL 内缓存影响。
- [ ] **CACHE-05 在途请求冻结**：使用可人工延迟的测试上游，在请求取得 80% 快照后再保存 60%；该在途请求完成时仍按 80% 结算，之后的新请求按 60% 结算。
- [ ] **CACHE-06 Redis 禁用**：禁用 Redis 后读取和保存规则，确认直接使用数据库权威状态，账单不变，不因缓存不可用自动按原价成功。
- [ ] **CACHE-07 Redis 丢键**：删除版本键或清空隔离 Redis 后请求，确认按数据库回源并恢复正确版本；不使用过期快照覆盖新规则。
- [ ] **CACHE-08 Redis 异常**：让 Redis 连接失败或超时，确认错误处理符合当前服务契约；不得把未知折扣静默降级为原价，也不得泄漏其他用户缓存。
- [ ] **CACHE-09 迟到回源**：在一次旧规则回源尚未完成时保存新规则，待旧回源返回后再次读取，确认旧 revision 不能覆盖新 revision。
- [ ] **CACHE-10 保存回滚**：让规则替换事务失败或回滚，确认 pending/fence 状态不会让未提交 revision 被当作有效折扣；后续请求最终回到数据库已提交版本。
- [ ] **CACHE-11 过期与淘汰**：等待 TTL 过期或在隔离环境淘汰本地缓存后重新读取，结果仍正确；缓存命中率变化不得改变账单。
- [ ] **CACHE-12 请求取消**：取消一个正在回源的请求，确认不会留下半成品缓存或影响后续请求；后续读取可正常取得完整快照。
- [ ] **CACHE-13 多会话改价**：两个管理员会话分别修改同一用户，确认 revision 屏障和 409 生效；不以页面最后返回时间覆盖服务器最新规则。
- [ ] **CACHE-14 用户 ID 复用边界**：删除用户后在隔离库创建新用户并复用可能的 ID，确认新用户不会命中旧用户的本地或 Redis 折扣。

## 8. 普通同步请求计费

对每个模型先做无折扣基线，再只改变用户模型折扣。每次从同一条消费日志读取真实用量和原价，按当前路径既有取整规则核算：

```text
折前费用 = Q(模型费用 + 不参与用户折扣的附加费)
折后费用 = Q(模型费用 * 折扣 + 不参与用户折扣的附加费)
优惠金额 = 折前费用 - 折后费用
```

`Q` 必须沿用该计费路径已有的换算、取整、最低额度和免费规则，不能用折后整数除以折扣反推折前费用。

### 8.1 基本金额和边界

- [ ] **BILL-01 无规则原价**：`USER-C` 请求 `M-RATIO`，折前等于折后，优惠为 0；用户、令牌和日志沿用原价口径。
- [ ] **BILL-02 100% 原价**：为 `USER-A` 提交 100%，请求结果与无规则原价完全一致，独立表不保存该规则。
- [ ] **BILL-03 普通倍率 80%**：对 `M-RATIO` 设置 8000，验证折后模型费用按 80% 计算；例如基线折前为 4000 时，折后应为 3200，优惠为 800，实际用量变化时按同一公式核算。
- [ ] **BILL-04 固定价格 80%**：对 `M-FIXED` 设置 8000，验证固定费用也套用用户模型折扣；例如基线折前为 5000 时，折后应为 4000，优惠为 1000。
- [ ] **BILL-05 阶梯/表达式 80%**：对 `M-TIERED` 设置 8000，覆盖至少一个阶梯边界，确认先按实际用量求模型费用再套折扣，不把阶梯单价或单位错误重复折扣。
- [ ] **BILL-06 最低折扣 0.01%**：设置 1，验证正费用不会溢出、变成负数或被错误当成免费；最低额度规则按该计费路径执行。
- [ ] **BILL-07 免费模型/免费分组**：对免费模型或免费分组配置折扣，确认费用仍为 0，日志不会生成负优惠，渠道统计不被伪造增加。
- [ ] **BILL-08 同一请求只折扣一次**：检查模型倍率、分组倍率、适配器倍率和用户折扣组合，确认用户折扣未被重复套用，也未被上游模型别名覆盖。
- [ ] **BILL-09 大小写和别名**：分别用原始模型名、计费别名、修饰符和大小写变化请求，确认管理配置、价格展示、预扣和最终结算命中同一条预期规则。
- [ ] **BILL-10 无用量响应**：上游返回无有效 token/用量时，确认遵循原有免费/最低额度语义，不通过缺失用量推导出错误优惠。

### 8.2 请求类型和流式

- [ ] **BILL-11 非流式文本**：验证 OpenAI/Claude/Gemini 等当前启用的非流式文本入口，折前、折后、优惠、钱包、令牌和渠道金额一致。
- [ ] **BILL-12 流式文本**：验证正常结束、客户端主动断开和上游流中错误；累计实际用量只结算一次，折扣与非流式口径一致。
- [ ] **BILL-13 Responses/特殊文本格式**：对 Responses 或目标版本启用的其他文本格式执行同一 80% 规则，确认不会绕过折扣或重复预扣。
- [ ] **BILL-14 图片**：验证不同数量、分辨率或质量档位，确认图片数量等倍率先按既有上限和计费规则校验，再按用户模型折扣计算，不能产生负费用。
- [ ] **BILL-15 Embedding/重排**：分别验证 token 用量和批量输入，确认用户折扣命中实际计费模型，渠道使用金额仍为折前。
- [ ] **BILL-16 音频/实时音频**：验证音频增量预扣和最终用量结算，确认同一段用量不重复扣费，连接中断有正确退款或调整。
- [ ] **BILL-17 Playground**：从 Playground 发起真实消费，确认使用同一用户折扣语义，并保留 Playground 既有令牌处理契约。
- [ ] **BILL-18 渠道测试**：执行渠道测试请求，确认渠道测试不套用用户模型折扣、不扣用户实际额度，行为与原有渠道测试一致。
- [ ] **BILL-19 工具附加费**：触发带工具/插件附加费的请求，确认模型费用按折扣，工具附加费按原有规则不折扣，三项金额可解释。
- [ ] **BILL-20 违规费用**：触发隔离环境中的违规费用流程，确认违规费用折前、折后相等，优惠为 0，不因用户模型折扣降低处罚金额。

## 9. 钱包、令牌、订阅和失败补偿

- [ ] **FUNDS-01 用户钱包扣减**：折扣 80% 请求成功后，用户钱包只减少折后费用；以日志实际 `quota_after_discount` 对账，不以 UI 四舍五入数字对账。
- [ ] **FUNDS-02 令牌扣减**：使用绑定令牌请求，确认令牌承担折后费用，用户钱包不重复扣同一笔，令牌日志与用户日志关联正确。
- [ ] **FUNDS-03 订阅余额**：在订阅有效和即将用尽两种状态下请求，确认折扣与订阅既有优先级一致，不因折扣绕过订阅限制或多扣一份费用。
- [ ] **FUNDS-04 无限令牌**：使用无限额度令牌，确认额度限制行为沿用原有契约；若仍产生消费统计，折前/折后和渠道金额保持正确，不把无限额度误当成免费模型。
- [ ] **FUNDS-05 折后足额**：设置余额低于折前但高于折后，验证请求按产品设计可成功，预扣使用折后金额，最终结算不再重复扣整笔。
- [ ] **FUNDS-06 折后不足**：设置余额连折后也不足，验证请求在上游调用前被拒绝，用户、令牌、渠道和日志不产生虚假成功扣款。
- [ ] **FUNDS-07 上游失败**：预扣成功后让上游返回失败，确认按原有补偿流程退回用户/令牌预扣，不产生重复退款；渠道统计与失败请求的既有口径一致。
- [ ] **FUNDS-08 中途断流**：预扣后客户端断开或上游中途断开，确认结算/退款只执行一次，最终用户余额不低于应有余额，日志能关联原请求。
- [ ] **FUNDS-09 结算金额变化**：让最终实际用量小于和大于预估值，分别验证折后差额的退款和补扣；渠道侧差额按折前值处理。
- [ ] **FUNDS-10 多承担方隔离**：分别用用户钱包、令牌、订阅额度完成同一模型请求，确认实际承担方只有一个，不出现用户和令牌同时扣除整笔费用。

## 10. 异步任务全链路

对目标环境实际启用的任务平台至少选择视频、MJ、音频或其他原生任务各一条。任务提交、轮询和终态结算必须保存任务 ID 及每次响应。

- [ ] **TASK-01 提交预扣**：以 80% 折扣提交任务，确认预估费用按折后值预扣，提交失败时没有孤儿任务或无法解释的余额扣减。
- [ ] **TASK-02 提交快照**：检查任务 `private_data.discount_amounts` 或 MJ `properties.new_api_discount_amounts`，确认保存折前总额、折后总额、优惠金额及必要的折扣快照，并标记 `discount_cost_scope=task_total`。
- [ ] **TASK-03 改价后轮询**：任务提交后把用户折扣从 80% 改为 60%，再轮询并完成任务；该任务仍按提交时 80% 快照结算，新任务才使用 60%。
- [ ] **TASK-04 表达式任务**：验证任务表达式计费按实际任务单位和目标版本表达式求值，再套用户折扣；不能把普通文本的每百万 token 公式复制到任务路径。
- [ ] **TASK-05 适配器调整路径**：验证上游返回最终时长、分辨率、质量或其他调整值时，用户用折后差额，渠道用折前差额；不重复套折扣。
- [ ] **TASK-06 token 重算路径**：验证任务最终按 token 重算的分支，折扣快照仍有效，预扣和终态只结算实际差额一次。
- [ ] **TASK-07 视频任务**：验证成功、失败、超时和上游无效结果；成功能正确保存最终媒体信息，失败按任务既有退款口径处理，折前/折后金额不反推。
- [ ] **TASK-08 MJ/换脸任务**：验证 MJ 或换脸的提交、轮询、补扣和退款；MJ 保留 `properties` 中原有状态及折扣键，不被上游同名字段覆盖。
- [ ] **TASK-09 音频/其他任务**：验证目标环境实际开启的异步音频或其他平台，确认用量、任务状态和折扣快照不依赖某一个适配器的特殊字段。
- [ ] **TASK-10 remix/续作**：基于旧任务创建 remix/续作，确认使用新请求取得的用户折扣和新任务参数，不继承旧任务用户折扣；允许继承的时长等参数仍按既有规则继承。
- [ ] **TASK-11 失败全退**：任务在已预扣后失败，确认用户/令牌折后预扣完整释放或按原有失败口径处理，渠道折前统计不被错误记为折后。
- [ ] **TASK-12 任务补扣**：最终金额高于预估时，用户/令牌只补扣折后差额，渠道调整折前差额；两者不能都使用同一折后差额。
- [ ] **TASK-13 任务退款**：最终金额低于预估时，用户/令牌退折后差额，渠道调整折前差额；折后差额为 0 但折前发生变化时，渠道仍正确更新。
- [ ] **TASK-14 零差额**：最终金额与预扣相等时不重复扣款、不重复退款；必要的渠道统计和任务快照仍保持一致。
- [ ] **TASK-15 重复终态**：重复轮询、重复收到成功/失败终态、重复执行补偿，确认不会重复扣款、退款或追加任务总额。
- [ ] **TASK-16 进程重启**：任务提交后重启测试服务，再轮询到终态，确认使用持久化折扣快照，不回读当前用户新折扣，也不清除目标任务状态。
- [ ] **TASK-17 历史任务**：处理没有折扣金额快照的旧任务，确认沿用原有可靠额度口径，不用折后金额反推虚假的折前金额；损坏快照要明确报错或进入既有人工处理路径。
- [ ] **TASK-18 上游同名字段**：构造上游属性包含同名折扣字段的响应，确认站内提交快照优先，上游不能篡改结算金额。

## 11. 日志、渠道统计和对账

### 11.1 普通消费日志

- [ ] **LOG-01 三项金额存在**：普通成功消费日志包含 `quota_before_discount`、`quota_after_discount`、`discount_quota`。
- [ ] **LOG-02 三项恒等式**：逐条核对 `quota_before_discount >= quota_after_discount >= 0`，且 `discount_quota = quota_before_discount - quota_after_discount`。
- [ ] **LOG-03 实际用量一致**：折前和折后来自同一次实际用量、同一模型和同一组倍率，不能用两次请求或折后金额反推折前。
- [ ] **LOG-04 原价日志**：无折扣、100% 折扣、免费模型和违规费用的日志三项值符合各自原有语义，优惠不出现负数。
- [ ] **LOG-05 用户可见性**：普通用户查看自己的日志时只能看到产品允许公开的金额字段；管理员查看时能核对折前/折后，敏感内部字段仍按权限隔离。
- [ ] **LOG-06 多用户隔离**：连续产生 A、B、C 三名用户日志，按 request ID 和 user ID 对照，确认折扣值不会被下一条请求覆盖。

### 11.2 任务调整日志

- [ ] **LOG-07 任务总额标记**：异步任务调整日志含 `discount_cost_scope=task_total`，并明确三项金额代表任务总额，而非单次流水金额。
- [ ] **LOG-08 不重复累计**：同一任务多次轮询或多条调整日志不能把多条任务总额直接相加造成重复统计；按原有调整差额对账。
- [ ] **LOG-09 任务方向**：补扣、退款、失败补偿分别核对用户折后方向和渠道折前方向，日志金额与余额变化一致。
- [ ] **LOG-10 快照损坏可见**：折扣金额快照缺失、非法或 JSON 损坏时不生成看似完整的推算三项金额，错误可定位到 task ID。

### 11.3 渠道使用金额

- [ ] **LOG-11 渠道折前统计**：普通请求和任务调整都核对渠道 `used_quota` 增量使用折前费用，不能跟随用户折扣减少。
- [ ] **LOG-12 分组倍率包含**：渠道折前值包含系统既有分组/站点倍率，不能误当成供应商实际成本；同一请求的用户折后值和渠道折前值都可由基线价格解释。
- [ ] **LOG-13 任务差额**：任务最终用量变化时，渠道按折前差额更新；即使用户折后差额为 0，渠道折前变化仍不能遗漏。
- [ ] **LOG-14 失败补偿**：上游失败、任务失败和退款场景按原有渠道统计方向对账，不出现渠道统计使用折后值、重复扣或重复退。
- [ ] **LOG-15 主库/日志库**：若环境启用了独立日志库或 ClickHouse，分别确认日志写入和金额字段可查询；关系库通过不代表日志库自动通过，也不能假设存在未实现的 outbox/收据 exactly-once。

## 12. 数据库兼容性人工冒烟

以下三类数据库分别在隔离环境执行最小完整链路：初始化两表、配置规则、读取缓存、完成一个普通请求、完成一个异步任务、清空规则和重复启动。

- [ ] **DBCOMP-01 SQLite**：验证事务、版本初始化、唯一约束、规则替换、删除和重复启动；不依赖 SQLite 不支持的 `FOR UPDATE`。
- [ ] **DBCOMP-02 MySQL**：验证 MySQL >= 5.7.8 的建表、唯一索引、事务锁和版本冲突；确认没有重复迁移。
- [ ] **DBCOMP-03 PostgreSQL**：验证 PostgreSQL >= 9.6 的建表、唯一索引、事务锁、版本冲突和失败回滚；确认唯一冲突不会污染失败事务。
- [ ] **DBCOMP-04 旧业务数据**：每种数据库都预置旧用户、任务、日志和渠道累计使用金额，启用功能后确认历史渠道金额保持原口径，不回填或反推折前费用。
- [ ] **DBCOMP-05 数字边界**：验证 revision 在前端安全整数范围内正常递增，非法超界 revision 被拒绝；折扣和额度不发生整数溢出或负数。

## 13. 故障和恢复

故障注入只在隔离环境进行，恢复后重新执行一条成功请求和一条失败请求，确认系统回到可解释状态。

- [ ] **FAIL-01 数据库读取失败**：折扣数据库读取失败时返回明确错误，不静默按原价计费。
- [ ] **FAIL-02 数据库写入失败**：规则保存失败时 revision、规则表、缓存屏障和页面提示一致，不返回成功。
- [ ] **FAIL-03 规则表部分约束失败**：制造唯一键或字段约束错误，确认整个规则替换回滚，不留下半套规则。
- [ ] **FAIL-04 Redis 恢复**：Redis 暂停后恢复，数据库规则和新旧 revision 均能正确读取，旧缓存不能重新覆盖新规则。
- [ ] **FAIL-05 令牌/钱包写入失败**：模拟承担方写入失败，确认上游调用、任务状态和补偿流程遵循原有顺序，不返回虚假成功。
- [ ] **FAIL-06 日志写入失败**：模拟日志库不可用，确认错误可见且不会用成功日志掩盖账务失败；按现有系统对账流程记录残留状态。
- [ ] **FAIL-07 任务 JSON 回写失败**：任务金额快照写入失败时不能继续以“已保存快照”结算；恢复后不会重复补扣或退款。
- [ ] **FAIL-08 客户端重试**：对保存、普通请求和任务轮询分别人工重复发送同一请求，确认可重试路径不重复扣退；失败路径不会被伪造成成功。

## 14. 结果判定和问题分级

出现以下任一情况，整条链路直接判定不通过：

- 用户被多扣、少退、负扣费，或同一请求发生重复扣款/退款。
- 折扣跨用户、跨令牌、跨任务污染；改价后新请求仍长期使用旧规则，或在途请求被中途改价。
- 未授权管理员能读取或修改其他用户规则。
- 折前/折后/优惠三项不能由同一次实际用量核对，或恒等式不成立。
- 渠道 `used_quota` 错误使用折后金额，导致渠道累计使用金额被用户折扣影响。
- 异步任务轮询重新读取当前折扣，或任务重试、重复终态造成重复结算。
- 规则保存返回成功但数据库、revision、缓存或页面其中一层没有对应结果。

建议分级：

| 级别 | 判定示例 |
| --- | --- |
| P0 | 余额/令牌被错误扣退、负费用、跨用户或未授权访问、折扣导致账务不可恢复 |
| P1 | 折前/折后或渠道金额错误、任务快照失效、重复结算、版本冲突覆盖、数据库迁移破坏既有数据 |
| P2 | 搜索/筛选结果延迟、抽屉加载需手动触发、布局错位、错误提示不清、非核心日志字段缺失 |

每个缺陷至少附：复现账号、模型、分组、折扣基点、revision、请求/任务 ID、数据库和 Redis 状态、操作顺序、实际与预期金额、响应原文、日志截图和是否影响历史数据。
